## What this decides

1. `mnemo init` with no passphrase makes a random 256-bit key, protects
   the file with the raw-key KDF parameters, and keeps the key in the OS
   keychain. Only a machine-made key ever opens a light-KDF file.
2. A compaction keeps the file's salt and KDF parameters, so the
   keychain entry, which is found by the salt, survives `mnemo compact`
   and `rekey --rotate`. A rekey still draws a new salt.
3. The key can be written down and typed back as a **recovery code**:
   Crockford Base32, a version prefix, and thirteen groups, each with its
   own check character, so a typo is reported by group.
4. Every surface (the CLI, the MCP server, Python) finds its secret through
   **one chain of sources** in one order, which ends at the keychain. With
   no keychain, nothing is written to a plain file unless the user names
   that file.
5. The rules on where key material may appear and where a key source may
   come from, and a plain statement of what the keychain does and doesn't
   protect.

## Where things stand today

- **Two KDF settings** (`mnemo/src/crypto.rs:55-90`):
  - `KdfParams::secure()` is 19 MiB and 2 passes, for passphrases.
  - `KdfParams::raw_key()` is the Argon2id floor, 8 KiB and 1 pass. Its
    doc says it's for a uniformly random 256-bit key and never for a
    human passphrase.
  - `KdfParams::fast()` (512 KiB, 1 pass) is for tests.
- **The key wrap** (`crypto.rs:97-124`, `248-278`):
  - `derive_kek(secret, salt, params)` turns the secret into the
    key-encryption key.
  - That key wraps the file's random data key with AES-256-GCM under a
    random 96-bit nonce.
  - The header holds the salt (bytes 86..102), the nonce (102..114), the
    wrapped data key (114..162) and the three KDF costs in the clear. The
    v9 seal authenticates all of them (`format.rs:137-156`).
- **Creating** (`store/open.rs:236-300`) draws a fresh salt and a fresh
  data key every time. `create_with_key` (`:199`) records `raw_key()`.
- **Compaction** (`store/maintenance.rs:776-822`) opens the old file, then
  builds the new one through `create_temp` → `create_secret_new` →
  `create_secret_as`.
  - That gives the new file a fresh data key, which is what a rotation
    needs.
  - It also gives the new file a fresh salt, which a keychain entry keyed
    by the salt can't survive (R-007.4).
  - The KDF parameters are carried over (`kdf = old.kdf`, `:795`).
- **Rekey** (`maintenance.rs:176-215`) draws a new salt and re-wraps the
  same data key. `mnemo rekey --rotate` is a rekey followed by a
  compaction (`bin/mnemo.rs:1576-1619`).
- **Secrets on the surfaces:**
  - **The CLI** takes `--passphrase` (with a warning), then
    `MNEMO_PASSPHRASE`, then a no-echo prompt when stdin is a terminal
    (`bin/mnemo.rs:934-955`).
    - Some commands take `--key-file` (32 raw bytes or 64 hex digits,
      `inspect.rs:58-77`), which overrides the passphrase sources.
    - The key file's permissions aren't checked.
    - `init` takes a passphrase only and double-prompts for it.
  - **The MCP server** reads `MNEMO_PASSPHRASE` and nothing else
    (`mcp.rs:233`). It never prompts, because stdio carries JSON-RPC.
  - **Python:**
    - `mnemo.open(path, passphrase, …)` needs a passphrase, and creates
      the file when it's missing.
    - `open_with_key` takes raw key bytes.
    - `rekey(new_passphrase, fast=False)` takes its KDF parameters from
      the file.
  - **The Swift and Kotlin packages** keep raw keys in the iOS Keychain or
    Android Keystore. Each item is found by a UUID stamped on the file,
    with "the first stored key that opens it" as a fallback. Nothing here
    changes them.

## 1. The generated key and the light-KDF rule

**The generated key.** `mnemo init <file>` with no passphrase source
(since RB-009, the order):
1. draws 32 bytes from the OS CSPRNG (`Mnemo::generate_key`);
2. creates the brain under a temp name next to `<file>`, as compaction
   does (`create_temp`), with `create_with_key`, so the header records
   `KdfParams::raw_key()` and an open costs microseconds;
3. stores the key in the keychain under the new file's salt, and reads
   the entry back (section 4);
4. renames the temp file to `<file>`;
5. shows the recovery code under the display rule (section 7).

**If anything fails, nothing is left half done:**
- If storing or reading back the key fails, `init` removes the temp file
  and fails.
- A kill between steps 3 and 4 leaves a temp file that holds nothing, and
  maybe an entry for a salt nothing uses. `<file>` doesn't exist, so the
  next `init` at that path works. It removes dead `init` temps the way a
  compaction removes dead compaction temps.
- So there's never a brain at `<file>` whose key is only in memory.

**Why the light parameters are safe for it.** Stretching makes each guess
of a weak secret expensive. A uniformly random 256-bit key can't be
guessed, so stretching it buys nothing: with the raw-key parameters
`derive_kek` is in effect a keyed hash of a full-entropy key. `age` makes
the same choice (scrypt for a passphrase, nothing for a key file). It's
safe only while **nothing but a machine-made key ever reaches a light-KDF
file**. These rules keep that true:

1. **A passphrase is never given parameters below `KdfParams::secure()`,
   whatever the file had.** One engine function picks the parameters for a
   passphrase. For each of the three costs it takes the larger of the
   file's value and `secure()`'s. It's used by every surface that rekeys
   to a passphrase or creates with one: the CLI's `init` and `rekey`,
   Python's `open` and `rekey` (on the plain and the shared handle), and
   uniffi's `create` and `export_rekeyed`.
2. **A passphrase with raw-key parameters is refused where every path
   meets** (since RB-009).
   - **Where:** the check sits in the internal create and the internal
     rekey (`create_secret_as`, `rekey_unchecked`), not in the public
     wrappers. Every create, rekey and export goes through them,
     `SharedMnemo::rekey` included, which calls `rekey_unchecked`
     directly.
   - **What it checks:** the secret arrives with its kind (passphrase or
     key) from the public function that took it. A passphrase with
     `m_cost` below `KdfParams::fast()`'s gets `MnemoError::Invalid`,
     naming `create_with_key` / `rekey_with_key` as the path for keys.
   - **The public functions it covers:** `Mnemo::create`, `rekey` and
     `export_rekeyed`, and `SharedMnemo::rekey`.
3. **`fast()` is the one exception** (since RB-009). It stays allowed
   with a passphrase, because the tests use it, and Python's `fast=True`
   passes it.
   - It's documented as a test switch, never for a real passphrase.
   - `mnemo info` shows a file with `fast()`'s parameters as "test-grade
     KDF parameters".
   - So "only a machine-made key ever opens a light-KDF file" holds for
     the raw-key parameters, and `fast()` is the named exception.
4. **A rekey from a key to a passphrase gets the full parameters**, by
   rule 1. A key-to-key rekey (`rekey_with_key`) records `raw_key()`, as
   now.
5. **`unlock` accepts only a well-formed recovery code** (section 5), and
   stores it only after it opens the file.
6. **A compaction never lowers the file's parameters, and it raises a
   passphrase file that's below the floor** (since RB-009).
   - Given a passphrase, on a file whose `m_cost` is below `fast()`'s,
     the compaction writes the new file with rule 1's parameters and
     keeps the salt.
   - The key-encryption key changes with the parameters. Nothing is
     keyed by them, so a keychain entry (which holds the secret, found by
     the salt) stays valid.
   - Otherwise it keeps the parameters, as now (section 2).
7. **A file below the floor is reported** (since RB-009). Its header
   can't say what kind of secret it takes, but an open can.
   - When a passphrase opens a file whose `m_cost` is below `fast()`'s,
     the handle gets a notice (the 12.4 `notices()` list, and Python's
     `UserWarning`).
   - `mnemo info` and `mnemo verify` print a line.
   - The fix is named: "`mnemo rekey` or `mnemo compact` raises the
     parameters". That covers the passphrase entry points, the chain's
     passphrase source and shared opens.
8. **What the rules can't reach.** A key file or `MNEMO_KEY` holding 64
   hex digits a person typed in by hand is a key by its shape. The docs
   say to make keys with `mnemo init` (or `openssl rand -hex 32`), never
   by hand.

**The CHANGELOG** (since RB-009) says, under v0.15.0: "passphrase KDF
parameters now have a floor, and `mnemo info` reports a file below it,
which `mnemo rekey` or `mnemo compact` fixes".

## 2. The salt rule (R-007.4)

**A compaction keeps the old file's salt and KDF parameters.**
- The new file still gets a fresh data key, wrapped under a fresh random
  nonce.
- The key-encryption key is the same, because the secret and the salt
  are. So whatever found the key for the old file finds it for the new
  one.

**A rekey draws a new salt, as today.** The secret changes, so the
keychain entry has to be rewritten anyway (section 4 gives the order).

**What follows, per operation:**

| Operation | Salt | KDF parameters | Data key | Keychain entry |
|---|---|---|---|---|
| `mnemo compact` (any surface) | kept | kept, or raised for a passphrase below the floor (section 1, rule 6) | new | still valid |
| shared mode's compaction, `compact_file_waiting` | kept | as above | new | still valid |
| compacting a v8 file to v9 | kept (same header field) | as above | new | still valid |
| `rekey` | new | per section 1 | same | rewritten under the new salt |
| `rekey --rotate` | new (the rekey), then kept (its compaction) | per section 1 | new | rewritten once, under the rekey's salt |
| `export_rekeyed` | new | the caller's (section 1) | new | the copy is a new brain |
| copying the file (`cp`, `export_encrypted`) | the same bytes | same | same | the copy uses the same entry |

**Why reusing the salt across compactions is safe.**
- The salt keeps two files' key-encryption keys apart when they share a
  secret, and stops guesses from being computed ahead for every file at
  once.
- Across a compaction the files share the secret, so anyone who can derive
  one key-encryption key can derive the other anyway. Keeping the salt
  gives nobody a key they didn't already have.
- The old copy and the new file keep different data keys. Rotation is
  about the data key, and it's unchanged.
- Each compaction adds one wrap under the same key-encryption key with a
  fresh random 96-bit nonce. A brain is compacted a few thousand times in
  its life at most, far below the bound on random nonces under one key.
- **A swapped header doesn't get around it** (since RB-009). Putting the
  old file's header, with its wrap, onto the new file unwraps the old
  data key. That key doesn't verify the new file's v9 header seal, which
  covers the salt, the nonce, the wrapped key and the KDF costs, nor its
  pages. So the open fails, as it does for any foreign header today.

**The code change.**
- `create_secret_as` gets an internal variant that takes the salt instead
  of drawing one (`pub(super)`, never public).
- `create_temp` passes the old header's salt when it's called from
  `compact_file_secret`.
- The export path keeps drawing a fresh salt.
- The derived key-encryption key isn't kept between the two files. The
  new file derives it again, at one KDF's cost, as today.

## 3. The recovery code

**What it encodes:** the 32-byte key and nothing else. `unlock <file>`
reads the salt from the file's header, which needs no key. So the code
doesn't need to name the file, and it can't be pasted against the wrong
file without the open failing.

**The format, version 1:**
- **Alphabet:** Crockford Base32, `0123456789ABCDEFGHJKMNPQRSTVWXYZ`
  (no I, L, O or U), shown in upper case.
- **Data:** the key's 256 bits, most significant first, followed by four
  zero bits, make 52 symbols. The last symbol holds one key bit, so it's
  `0` or `G`.
- **Groups:** thirteen groups of four data symbols. Each gets a fifth
  symbol, its check (below), so a group is five characters on screen.
- **The prefix:** `MN1`, where `1` is the format version. A later format
  changes the digit.
- **As shown:** `MN1-` and the thirteen groups joined by hyphens, 68
  symbols with 13 hyphens.

**The check symbol of group `i`** (counting from 0) with data symbols
`d0 d1 d2 d3`, each taken as a 5-bit value:

```
c = i ⊕ α·d0 ⊕ α²·d1 ⊕ α³·d2 ⊕ α⁴·d3
```

- The arithmetic is in GF(32), with the polynomial x⁵ + x² + 1.
- `α` is x (the value 2), and `⊕` is XOR.
- `α` generates the whole field, so `1, α, α², α³, α⁴` are five
  different non-zero values.

The check is a linear code, which gives three guarantees. Each was tested
exhaustively on random groups:
- **Any one wrong character in a group is caught,** the check character
  included. Each position's weight is non-zero.
- **Any two characters swapped within a group are caught,** wherever they
  are. The weights are all different, and `α^k ⊕ 1 ≠ 0` for `k` from 1 to
  4.
- **A whole group typed in another group's place is caught.** The group's
  index is part of its check, with weight 1.

Two wrong characters in one group are caught 30 times in 31 (since
RB-009). For any first error, exactly one of the 31 possible values of a
second error at another position cancels it.

**A whole-code check isn't needed.** `unlock` and every open test the key
against the file's wrapped data key, which is authenticated encryption:
a wrong key fails for certain. The per-group checks are there to say
*where* the typo is.

**Worked example.** The example key is the bytes `00 01 02 … 1f` (not a
real key):

```
MN1-000GD-40R4X-0M300-E209K-185G3-R38ED-1W811-24GKZ-2GAH1-C5RR2-34D1B-P70XX-3RFGZ
```

Group 1 (the second group) is `40R4` with check `X`:

| | `i` | `4` | `0` | `R` | `4` |
|---|---|---|---|---|---|
| value | 1 | 4 | 0 | 24 | 4 |
| weight | 1 | α = 2 | α² = 4 | α³ = 8 | α⁴ = 16 |
| product in GF(32) | 1 | 8 | 0 | 30 | 10 |

- The XOR of the products is `1 ⊕ 8 ⊕ 0 ⊕ 30 ⊕ 10 = 29`, which is `X`.
- For example, α⁴·4 = x⁶ = x·x⁵ = x·(x² + 1) = x³ + x = 10.

The last group, `3RFG`, ends in `G`: one key bit, then four zero bits.

The step-1 code carries this example as a known-answer test, in Rust. The
script that checked the guarantees isn't committed.

**Reading a code back:**
- Case is ignored, and so are spaces. `I` and `L` read as `1`, and `O`
  as `0`, as Crockford's alphabet says. That applies to the prefix too,
  so `MNI-…` and `MNl-…` read as `MN1` (since RB-009). `U` and anything
  else outside the alphabet is an error that names the character and its
  group.
- The prefix must be `MN1`. A different version says "made by a newer
  mnemo".
- **The length must be exactly 65 symbols after the prefix.** When it
  isn't (since RB-009):
  - **With hyphens in the typed text,** splitting on them gives the
    groups as the person typed them, and the group that isn't five
    characters long is named: "group 4 has 4 characters, 5 expected".
  - **Without hyphens,** the error gives the count, and names the first
    group whose check fails as "group N or the one before it". A missing
    or extra character usually shows up there first, and sometimes one
    group later.
  - When every complete group checks out, the last group is named. The
    missing or extra character is then in it.
  - Groups are counted from 1 in messages; the formula counts from 0.
- **Otherwise hyphens are ignored** wherever they are.
- **With the right length**, every group whose check fails is named.
- **The last data symbol must be `0` or `G`.** That keeps a key to one
  spelling, and anything else names group 13.
- The parsed key is zeroized when it's dropped, and so is the typed text.

## 4. The keychain entry

**What it holds:**
- **The name:** service `io.github.toarchkumar.mnemo.brain`, account the
  salt in lower-case hex (32 characters).
  - The Swift package's items use a different service and accounts that
    are UUIDs, so the two never collide.
  - The file's path is put in the item's label, for a person browsing the
    keychain. Nothing looks an entry up by path, so moving or renaming
    the file doesn't orphan it.
- **The value:** `key:` and 64 hex digits for a key, or `passphrase:` and
  the passphrase, for step 3's "move `MNEMO_PASSPHRASE` into the
  keychain". The type is stored so an entry is never guessed.

**When a rekey rewrites it.** In this order, so a crash at any point
leaves a secret that opens the file (since RB-009, steps 3, 4 and 6):
1. Draw the new key (for `--new-key`) and the new salt.
2. Store the new secret under the new salt.
3. Read the entry back, and check it's the secret just stored. If it
   isn't, delete it and stop before anything is committed.
4. With `--new-key`, show the new recovery code now, under the display
   rule (section 7), before the commit. If the rule doesn't hold, say
   that `mnemo recovery-code <file>` shows it later.
5. Commit the rekey.
6. **After any error from the commit, look before deleting anything.**
   - Read page 0 again, or, when it doesn't parse, the header candidate
     an open would recover to.
   - **If it still has the old salt,** REKEY-1 left the old secret in
     force, and the new entry is deleted.
   - **If it has the new salt,** this is REKEY-1's one exception ("may
     open with either secret"), and after a close the file opens with
     the new secret only. Both entries are kept, and the message says
     so.
   - If neither can be read, both are kept.
   - **Whenever the error is REKEY-1's exception, both are kept, whatever
     page 0 reads** (step 1's code). A failed write can still land later,
     and with injected failures page 0 reads as the old salt in exactly
     this case.
7. Keep the old entry. Copies of the file made before the rekey still use
   it, and `mnemo` can't know whether any exist. The message says the old
   entry is still there. Removing old entries is a later command (see
   "For sign-off").

**A power cut between steps 2 and 5** (since RB-009):
- The commit is synced. Whether the store has made the new entry durable
  by then depends on the store.
- If it hasn't, a power cut after the commit leaves the file under the
  new salt with no entry for it.
  - With `--new-key` at a terminal, step 4 showed the code, so its owner
    has it.
  - With a passphrase, the person typed it.
  - Without the display rule, the key would exist nowhere.
- Whether each store's write is durable when it returns is one of step
  2's questions about the store crates. If a store can't say, step 2
  makes `--new-key` without the display rule refuse on that store, unless
  the user names a key file to write as well.
- **Step 2's answer:** none of the three stores (`keyring` 3.6.3's macOS,
  Windows and Secret Service stores) documents a durable write. So the
  rule applies to all of them: `rekey --new-key` refuses when the display
  rule doesn't hold, unless `--new-key-file <PATH>` writes the key to a new
  0600 file before the commit. `rekey --help` says so.

So the engine's rekey has to let the caller store the secret after the
salt is drawn and before the commit. It does this with a hook on the rekey
call, not a public "rekey with this salt".

**`mnemo rekey` on a brain whose secret came from the keychain:**
- `--new-key` makes a new generated key and shows its recovery code
  before the commit (step 4 above; section 7).
- Otherwise the new secret is a passphrase, as today, with the full
  parameters (section 1). Its entry is written only when the user asks
  (`--store`), and otherwise the keychain is left alone.
- `--rotate` works with either, as today.

## 5. `recovery-code` and `unlock`

**`mnemo recovery-code <file>`** (step 1) shows the code of the key the
keychain holds for this file.
- It refuses when the entry is a passphrase ("this brain uses a
  passphrase; there's no recovery code").
- It refuses when the stored key doesn't open the file (`key_opens`), and
  says so, rather than show a code that would lock its owner out.
- It shows the code only under the display rule (section 7).
- On macOS, reading the item can ask the user for access. That prompt is
  the authentication step R-007.5 rec. 3 asks for.

**`mnemo unlock <file>`** (step 2) imports a recovery code into this
machine's keychain.
- **Input:**
  - It reads the code from a no-echo prompt when stdin is a terminal, and
    from stdin otherwise (`… | mnemo unlock <file>`, for scripts).
  - **It never takes the code as an argument.** There is no such argument,
    so it can't end up in shell history or a process listing.
  - From stdin, it reads the first line, up to 256 bytes.
- **Checks, in order:**
  1. The format (section 3), with the group named.
  2. The key opens this file (`key_opens`, header only).
  3. The file's KDF parameters are the raw-key ones. A passphrase file
     can't be opened by a recovery code anyway; this makes the message
     say so.
- **The entry:**
  - If an entry for this salt exists and opens the file, it says "already
    unlocked" and changes nothing.
  - If one exists and doesn't open the file, it's replaced, and the
    message says so.
- **No keychain:** `unlock` says so and points at `MNEMO_KEY` (which
  accepts the recovery code, section 6) and `--key-file`. It writes no
  file.

## 6. The key-source chain

**One order for every surface**, used when no flag on the command line
names a source:

| # | Source | Holds | Where it may come from |
|---|---|---|---|
| 1 | `MNEMO_PASSPHRASE` or `MNEMO_KEY` | a passphrase, or a key (64 hex digits or a recovery code) | the process environment |
| 2 | `MNEMO_KEY_FILE` | a key: 32 raw bytes, 64 hex digits, or a recovery code | the process environment |
| 3 | `MNEMO_KEY_COMMAND` | a command whose first line of output is a key, in the same forms | the process environment |
| 4 | the keychain | the entry for the file's salt (section 4) | the OS store |
| 5 | a prompt (the CLI only, when stdin is a terminal) | a passphrase | the person at the terminal |

**Flags name a source outright.** `--passphrase` and `--key-file` are
used as they are, and the chain isn't consulted, as `--key-file` works
today.

**The rules:**
- **The chain picks by the file's kind, without trying** (since RB-009).
  - It first reads the file's KDF parameters from page 0, which needs no
    key.
  - **A file with raw-key parameters** (`m_cost` below `fast()`'s) is a
    key file. It takes the first key source present: `MNEMO_KEY`,
    `MNEMO_KEY_FILE`, `MNEMO_KEY_COMMAND`, the keychain, in the table's
    order.
  - **Any other file** is a passphrase file. It takes the first
    passphrase source present: `MNEMO_PASSPHRASE`, a passphrase entry in
    the keychain (step 3's move), the prompt.
  - **A skipped source is named in the output**, not silently passed
    over. For example: "MNEMO_PASSPHRASE is set, but x.mnemo uses a key;
    using its keychain entry".
  - So one process can hold a key brain from the keychain and a
    passphrase brain from `MNEMO_PASSPHRASE`, the 12.4 note's project
    and personal brains. A `MNEMO_PASSPHRASE` left over from v0.14
    doesn't block a new key brain.
- **Within a kind there's no fall-through.**
  - The first source of the file's kind that's present is used. If it
    doesn't open the file, the error names it, and names the next source
    of that kind that's present. For example: "MNEMO_KEY is set and
    doesn't open x.mnemo; unset it to use the keychain entry this file
    has".
  - Trying each source in turn would hide a misconfiguration, cost a
    passphrase KDF for every wrong one, and make it unclear which secret
    opened a file. restic and borg also use the first source set.
- **When no source of the file's kind is present,** the first source of
  the other kind is used, once.
  - That's how a file with a passphrase on raw-key parameters (section
    1, rule 7) still opens. The open then reports it.
  - For a key file, that means `MNEMO_PASSPHRASE` if it's set. The prompt
    isn't offered for a key file: the error lists the key sources, and
    `--passphrase` for a file that was given one.
  - It's still one try, with nothing guessed.
- **Keys and passphrases don't mix.** `MNEMO_KEY`, key files and the
  command carry keys only.
  - Classifying a string by its shape would turn a 64-hex-digit
    passphrase into the wrong key.
  - A passphrase from a password manager goes into `MNEMO_PASSPHRASE` in
    the user's own shell profile.
- **Key files** must be regular files owned by the user, with no access
  for group or others (`mode & 077 == 0`) on Unix; anything else is
  refused, as `ssh` does. The refusal names the fix (`chmod 600 <path>`).
  This also applies to `--key-file`, which doesn't check today; the
  CHANGELOG says so. Windows isn't checked, and the docs say so.
- **The command** is split as `--embed-cmd` is (`embed_cmd.rs`,
  `shlex_split`, no shell) and run with:
  - stdin closed;
  - a timeout of 60 seconds in the CLI and 10 seconds in the MCP server
    (since RB-009). A server started by a client has no terminal, so a
    command waiting for a prompt would hold the server's start. The error
    says the key command didn't answer in time;
  - its exit status checked;
  - stdout capped at 4 KiB, with only the first line used, zeroized after
    use;
  - stderr passed through, so a password manager can ask its own
    questions.
- **The keychain lookup** reads the salt from page 0 without the key, as
  `peek_dimensions` reads the width.
  - **When page 0 doesn't parse** (a torn or zeroed first sector), there's
    no salt to look up, while the open would recover the header given the
    key.
  - **Step 2** (since RB-009) takes the candidate salts from the WAL's
    header frames, which are plaintext page-0 images. A key-free variant
    of the torn-header scan (`scan_header_recovery_candidates`,
    `store/open.rs:53`) does it.
  - Each candidate salt is looked up in turn, and an entry that's found
    goes through the normal open, which heals the header.
  - Its test: a key brain with page 0 zeroed opens with nothing typed.
  - **Windows, while a plain handle holds the lock** (step 2). The lock
    covers the whole file (`LockFileEx` from 0 for the full length), so the
    WAL can't be read either. A last-known salt would need a file beside
    the brain, which the single-file rule rules out. So the chain behaves as
    with no salt there, and `mnemo/README.md` says so. Shared handles hold
    nothing between calls, so they don't cause it.
- **The store is looked up last, and lazily** (step 2, PLANNER-A's
  finding): only when no environment source of the file's kind is set, or
  for the one try of the other kind.
  - A store error is a note when another source answers, and the error
    only when the store was the source left.
  - A store that can't be used here at all (its availability probe fails:
    no Secret Service on the session bus, no access) is no store (section
    8), so a headless Linux machine behaves as with no keychain.
- **Every surface reports which source opened the file.** `mnemo info`
  prints it, and the MCP server logs it to stderr at start. The secret
  itself never appears.

**Where each surface reads:**
- **The CLI:** the whole chain, after its flags.
- **The MCP server** (`serve --mcp`): sources 1 to 4, never a prompt.
  - With none, it fails at start, to stderr, listing the four sources.
  - It takes no key flag, so that what `mcp install` writes (step 3)
    carries no secret.
- **Python:** `mnemo.open(path, passphrase=None, …)`, where `None` means
  sources 1 to 4, never a prompt.
  - `None` with a missing file raises `ValueError` and names `mnemo init`.
    Creating with a generated key stays in the CLI, where the recovery
    code can be shown safely.
  - `open_with_key` is unchanged.
- **The Swift and Kotlin packages:** unchanged. They have their own key
  stores.
- **Shared mode (RB-006.11 (c)):**
  - A shared handle keeps its secret, as now.
  - For a key from sources 2 to 4, the key is all there is to keep, so
    fetching it again would change nothing (RB-006.11's own point 3).
  - For a passphrase from `MNEMO_PASSPHRASE`, the environment already
    holds it for the process's life.
  - So nothing changes in 12.3. Re-reading the source becomes worth it
    only once a passphrase can come from the keychain (step 3's move),
    and then it's the keychain read again.

## 7. Security rules for the design

Each rule below is built in steps 1 and 2, with the test named.

**The display rule: key material is shown only to a person at a
terminal** (since the sign-off; since RB-009, condition 4 and how it's
shown). `init`, `rekey --new-key`, `recovery-code` and `onboard` show a
recovery code only when all four of these hold:
1. stdout is a terminal;
2. stdin is a terminal;
3. no known agent-harness marker is set in the environment;
4. the controlling terminal can be opened (`/dev/tty` on Unix, the
   console's `CONIN$` and `CONOUT$` on Windows).

**How it's shown** (since RB-009). Everything goes through the
controlling terminal, never through stdout:
1. It asks first: "Press Enter to show the recovery code. Make sure this
   is your own terminal." It reads the answer from the controlling
   terminal, without echo.
   - A harness that runs the command and waits for it to end doesn't
     press Enter; a person does.
   - So this covers harnesses that aren't on the marker list better than
     the list can.
2. It switches to the terminal's alternate screen, and shows the code
   with a line telling the person to write it down.
3. It waits for another key press, then leaves the alternate screen.
   - Most terminals and multiplexers keep no scrollback of the alternate
     screen, so nothing is left behind to scroll back to.
   - A harness that captures stdout sees nothing at any point.

**The markers:**
- They're kept as one list in the `keys` module, starting with
  `CLAUDECODE`, which Claude Code sets in the shells it runs commands in.
- `AI_AGENT` is a candidate (since RB-009). It's added once its vendor's
  documentation is found and cited, like the others.
- Each marker is checked against the vendor's documentation before it's
  added, and the comment beside it cites that page.
- A marker only makes the rule stricter, never looser. Its value isn't
  read, only whether it's set and not empty.
- **The list is a best effort.** It can only name harnesses someone has
  checked, so the key press in step 1 is the guard that doesn't depend on
  it.

**When any condition fails:**
- They print no key material at all. The key is already in the keychain.
- The message is: "the recovery code wasn't shown, because this doesn't
  look like a terminal a person is at. Run `mnemo recovery-code <file>`
  in a terminal of your own, not through an agent's shell (for example,
  Claude Code's `!`)".
- So when an agent drives `init` or `onboard`, through a pipe or under a
  harness that sets a marker, the code stays out of its context and
  transcript, and the human gets the code directly.

**Tests:**
- `init` with stdout piped prints nothing from which the key could be
  rebuilt: no group of the code, no hex, no prefix followed by symbols.
  The test reads the stored key from the test key store and checks the
  output for every one of its four-symbol groups.
- The same with stdin piped and stdout a terminal.
- The same with `CLAUDECODE=1` set, under a pseudo-terminal where that's
  cheap to set up, and otherwise on the rule's function with the other
  checks true.
- The same with no controlling terminal (a process started with no
  terminal attached, `setsid` on Unix).
- With every condition true under a pseudo-terminal, nothing is shown
  until Enter is pressed, and the code goes to the controlling terminal,
  not to stdout.

**The limit:** the rule can't tell a person from a program that drives a
pseudo-terminal, sets no known marker and presses Enter. A harness that
reads the screen while the code is up can see it. That's stated in the
threat model below.

**Codes and keys are never arguments.**
- `unlock` reads from a prompt or stdin (section 5).
- No command takes a key, a recovery code or a key command on its command
  line. `--key-file` takes a path.

**Key sources come only from the user.**
- The engine reads sources from the process environment, its own command
  line and the OS keychain. It reads none from:
  - a file in a working tree (there's no project config file, and 12.3
    adds none);
  - the brain's own contents (its manifest and metadata can't name a key
    source or a command);
  - an MCP request.
- `MNEMO_KEY_COMMAND` runs a program, like `--embed-cmd`. So the docs say
  to set it only in the user's own environment or user-level config.
- Step 3's `mcp install` never writes it, nor `--embed-cmd`, into a
  project-scoped file.
- **The limit:** the engine can't tell where an environment variable came
  from. A project's environment file, loaded by the user's tooling, looks
  the same as the user's profile.

**No plain-text fallback.**
- With no keychain, `init` without a passphrase fails, and says which
  sources would work (section 8).
- A key is written to a plain file only when the user names the file
  (`init --key-file PATH`). That file is created new (`O_EXCL`) with mode
  0600.

**Key files open to group or others are refused** (section 6).

### Threat model: what the keychain protects

- **What it does:** keeps the key out of config files, dotfile
  repositories, backups, screen shares, shell history and process
  listings, and away from other users of the machine. The claim is "the
  key no longer sits in plain text", and that's the whole claim.
- **What it doesn't:** keep the key from programs running as the same
  user.
  - **On Linux,** an unlocked Secret Service collection can be read by any
    process on the user's session bus.
  - **On macOS,** access is granted per binary. A `cargo install` upgrade
    asks again, and "Always Allow" covers anything that can run that
    binary, an agent included.
  - **On Windows,** a Credential Manager entry can be read by the user's
    processes.

  These come from general knowledge and the stores' documentation. Step 2
  checks them for the `keyring` 4 store crates it picks.
- **`mnemo recovery-code`** can be run by any such program.
  - The display rule keeps the code out of piped output, out of
    harnesses that mark themselves, out of runs where nobody presses
    Enter, and out of scrollback. So it doesn't land in an agent's
    transcript by accident.
  - The marker list is a best effort.
  - The rule isn't a barrier against a program that sets out to read the
    key. One that drives a pseudo-terminal and presses Enter passes it,
    and any program can read the keychain entry directly.
- **The docs say this plainly**, in the README's security section and in
  `mnemo init --help`. The parts on the passphrase sources follow from
  the same point: whatever runs as the user can read what the user can.

## 8. With no keychain

"No keychain" means any of these:
- the `keychain` feature is off (library builds; it's on for the release
  CLI binaries and wheels, step 2);
- the store crate reports no store or no access;
- on Linux, no Secret Service on the session bus (headless servers,
  containers, CI, WSL without a session).

What each command does:
- **`init`** without a passphrase fails, creates nothing, and lists the
  choices. It leads with `--ask-passphrase`, because that's what a v0.14
  user typing `mnemo init` on a headless box expects:
  - `--ask-passphrase` (the double prompt v0.14's `init` showed), or
    `MNEMO_PASSPHRASE`;
  - `--key-file PATH`, which writes a new generated key to a new 0600
    file.

  The CHANGELOG states the change: `init` with no passphrase source now
  makes a key instead of prompting.
- **Opening** skips the keychain in the chain. With no other source, the
  error lists sources 1 to 3 (and the CLI's prompt, when stdin is a
  terminal).
- **`unlock` and `recovery-code`** say there's no keychain, and point at
  `MNEMO_KEY` and key files.
- **CI and containers** (since RB-009):
  - **First choice:** put the recovery code (or the 64 hex digits) in the
    platform's secret store and expose it as `MNEMO_KEY`. For example, a
    CI secret, or a Kubernetes `env.valueFrom.secretKeyRef`.
  - **A mounted key file must pass section 6's check:** owned by the user
    the process runs as, with mode 0400 or 0600.
    - The usual mounts don't do that as they come. A Docker secret is
      owned by root and readable by all, and a Kubernetes secret volume
      is 0644 unless `defaultMode` is set, and owned by root.
    - So the docs say how to set the owner and the mode: on Docker, the
      secret's `uid` and `mode`, or a copy made at start-up; on
      Kubernetes, `defaultMode: 0400` with a pod that runs as the owner,
      or an init step that copies the file.
    - The docs step checks these against Docker's and Kubernetes'
      documentation. They're from general knowledge here.
  - The repository's key-file fixtures are checked out 0644, so the tests
    that use them set their mode first.

Nothing in this list writes a key that the user didn't name.

## 9. How `onboard` (12.2) will call these

`onboard` runs the parts, and adds nothing of its own to the key path:
1. `init` with a generated key, kept in the keychain.
2. The recovery code, under section 7's display rule (stdout and stdin
   terminals, no agent-harness marker, a controlling terminal, and a key
   press). When the rule holds:
   - It shows the code on the alternate screen, then asks for the last
     group back. The answer is read without echo (since RB-009), so the
     group isn't on the screen a second time.
   - On a mismatch it shows the code again, up to three tries.
   - Then it goes on, and says the code wasn't confirmed.

   When it doesn't (an agent driving it, through a pipe or under a
   marked harness): no code is shown, and the human gets section 7's
   message, to run `mnemo recovery-code <file>` in a terminal of their
   own.
3. `mcp install` (step 3), which writes no secret, because the server
   finds the key through the chain.
4. The embedder's set-up (steps 4 and 5).

The library parts sit in one engine module (`mnemo_engine::keys`, the
name is open):
- the recovery code's encoder and parser;
- the key-store trait, with the OS keychain behind the `keychain`
  feature;
- the chain's resolver, which returns the secret and the source that gave
  it;
- the parameter choice for a passphrase (section 1).

The CLI, the MCP server and Python all call the resolver, so the chain is
written once.

## 10. What step 1's code covers, and the test list

**The split between steps 1 and 2.** The spec's end-to-end test ("`init`,
`compact`, `rekey --rotate`, then an open with nothing typed") needs a
key store before the OS keychain lands in step 2. So:
- **Step 1** defines the key-store trait and a test store, a directory
  chosen by a `MNEMO_DEV_KEYSTORE` switch that exists only with the
  `dev-hooks` feature, like the other `MNEMO_DEV_*` switches. Never in a
  release build.
- **Step 1 builds:**
  - `init`'s generated key (with `--key-file` and `--ask-passphrase`),
    created under a temp name;
  - the recovery code, and the display rule through the controlling
    terminal;
  - `recovery-code`;
  - `rekey --new-key`, with section 4's order;
  - the salt rule and the KDF rules, with the report and the heal;
  - the CLI's chain by kind, as far as the test store, the key command
    included.
- **Step 2** adds the OS keychain store (after the `keyring` 4 check),
  `unlock`, and the chain in the MCP server and Python.

**Tests in step 1:**
1. A compaction keeps the salt and the three KDF costs, and writes a new
   data key (the wrapped key and the nonce differ). Both the old copy and
   the new file open with the secret, and the old copy's data key doesn't
   open the new file's pages.
2. A rekey draws a new salt. `rekey --rotate` ends with the rekey's salt
   and a new data key.
3. A v8 fixture compacted to v9 keeps its salt.
4. A shared-mode compaction keeps the salt, and a shared handle follows it
   (an assertion added to an existing test).
5. **The KDF rules** (since RB-009, the shared rekey, the report and the
   heal):
   - A rekey to a passphrase from a raw-key file records at least
     `secure()`, through `Mnemo::rekey`, `SharedMnemo::rekey`, the CLI,
     and Python's plain and shared handles.
   - `create`, `rekey`, `export_rekeyed` and `SharedMnemo::rekey` with a
     passphrase and `raw_key()` return `Invalid`.
   - `fast()` still works for tests, and `mnemo info` calls it
     test-grade.
   - **A file that already has a passphrase on raw-key parameters** is
     made with a test hook, since the public paths refuse it. Opening
     it with the passphrase works and gives the notice; `info` and
     `verify` print the line; `compact` with the passphrase raises the
     parameters to `secure()` and keeps the salt, and the notice is gone.
6. **The recovery code:**
   - round trips on random keys, plus the known-answer example above;
   - every single substitution, every swap within a group and every group
     in another slot is caught and named;
   - lower case, hyphens, spaces and `I`/`L`/`O` are accepted, in the
     prefix too (`MNI`, `MNl`), and `U` is refused;
   - **a wrong length** (since RB-009):
     - with hyphens and one group short, that group is named;
     - without hyphens, "group N or the one before it" is named;
     - a character dropped from the last group names the last group;
   - a last symbol other than `0` or `G` is refused;
   - a wrong prefix is refused.
7. **The display rule** (section 7): `init` prints no key material with
   stdout piped, with stdin piped, with `CLAUDECODE=1` set, or with no
   controlling terminal. Under a pseudo-terminal, nothing is shown before
   Enter, and nothing goes to stdout.
8. `recovery-code` shows the stored key's code, refuses a passphrase
   entry, and refuses a key that doesn't open the file.
9. **The end-to-end:**
   - `init` (into the test store), then `compact`, then
     `rekey --rotate --new-key`, then `info` with nothing typed;
   - the same with `rekey --rotate` to a passphrase, which then opens
     from `MNEMO_PASSPHRASE` with the full parameters;
   - after the rekey, the old entry is still in the store.
10. **The chain** (since RB-009, by kind):
    - each source alone opens a file of its kind;
    - a recovery code works through `MNEMO_KEY` and through a key file;
    - `MNEMO_PASSPHRASE` set with a key brain is skipped and named, and
      the key source opens it;
    - a present source of the right kind that's wrong fails and names
      itself, with no fall-through;
    - a key brain with only `MNEMO_PASSPHRASE` set tries it once;
    - `--key-file` skips the chain.
11. **Key files:** mode 0644 is refused, naming `chmod 600`; 0600 and
    0400 are accepted (Unix).
12. **`init`:**
    - with no key store, `init` without a passphrase fails, creates
      neither the brain nor any key file, and leads with
      `--ask-passphrase`;
    - `init --key-file` makes a 0600 file and refuses an existing path;
    - **killed between storing the key and the rename** (a failpoint;
      since RB-009), it leaves no file at the path, and the next `init`
      there works and removes the dead temp.
13. **The rekey order** (since RB-009, the "either secret" case), with
    REKEY-2's failpoints:
    - a failure before page 0 lands removes the new entry and leaves the
      old secret working;
    - a failure of the write-back after page 0 landed keeps both entries,
      says so, and the file opens from the store after a close;
    - a read-back that doesn't match stops before the commit.
14. **The key command** (since RB-009): a non-zero exit, no output, more
    than 4 KiB of output, and a timeout each fail with their own message,
    and nothing is used.

**Tests in step 2:**
- `unlock`: input only from a prompt or stdin; groups named; a code that
  doesn't open the file isn't stored; "already unlocked"; a stale entry
  replaced.
- The MCP server and Python open through the chain, and the server's key
  command times out at 10 s.
- **Two brains in one process** (since RB-009): a key brain from the
  store and a passphrase brain from `MNEMO_PASSPHRASE`, both opened by
  one MCP server or one Python process.
- **A damaged page 0** (since RB-009): a key brain with its first sector
  zeroed opens with nothing typed, through the salts in the WAL's header
  frames.
- The OS store round trip, in CI where a store exists. Secret Service
  needs a session bus, so the Linux job may use the store crate's mock.
- Each store's write durability, as a question answered before the store
  is chosen (section 4's power-cut case).

## Format

**No format change.**
- The salt stays in its header field (bytes 86..102), now carried over by
  a compaction, and the v9 seal covers it as before.
- No header byte is added, the reserved bytes stay zero, and the key-slot
  run is untouched. 13.2's extra slots will have their own salts, and a
  compaction will keep those too by the same rule.
- The recovery code and the keychain entry live outside the file. That's
  where a secret belongs: the single-file invariant is about the brain,
  not its key.
- A file made with a generated key opens with v0.14 too (`open_with_key`,
  or `--key-file` with the key).

## For sign-off

These are choices the spec leaves open, or where this note reads it one
way. **PLANNER-A accepted all ten (2026-11-14).** On 1, "groups of four"
meant the data symbols. The notes on 4 and 10 are in sections 8 and 6.
1. **Groups of five on screen** (four data symbols and the check), where
   the spec says "groups of four, each with its own check character". The
   other reading, three data symbols and a check, makes 18 groups and 72
   symbols instead of 13 and 65.
2. **No fall-through in the chain,** with an error that names the next
   source (section 6). Since RB-009.1 this holds within the file's kind:
   the chain picks by kind first.
3. **Flags bypass the chain**, which keeps `--key-file`'s behaviour today.
4. **`init` with no source no longer prompts.** It generates a key, and
   `--ask-passphrase` asks for a passphrase. `MNEMO_PASSPHRASE` and
   `--passphrase` work as before.
5. **Old keychain entries stay after a rekey,** because copies may use
   them. A command to forget them (`mnemo keys forget`, say) can come
   later.
6. **Keys only, in `MNEMO_KEY`, key files and `MNEMO_KEY_COMMAND`.** A
   passphrase from a command is out of scope.
7. **The keychain names:** service `io.github.toarchkumar.mnemo.brain`,
   account the salt in hex, the value typed `key:` or `passphrase:`.
8. **The engine refuses a passphrase with raw-key parameters**, which is
   a new `Invalid` from public functions, `SharedMnemo::rekey` included
   since RB-009.4.
9. **A test key store** in step 1, behind `dev-hooks`, so the end-to-end
   test can run before the OS keychain lands.
10. **The key-file permission check** also applies to the existing
    `--key-file`, which is a behaviour change, noted in the CHANGELOG.
