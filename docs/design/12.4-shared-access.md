# 12.4 Shared access: design note

Status: **draft for PLANNER-A's sign-off** (2026-11-13, Worker). No 12.4 code
exists yet. Spec: PLAN.md, Phase 12, section 12.4, plus the 2026-11-13
dispatch's eight additions. Code references are to `main` at `233eba4`
(v0.13.2).

## Recommendation

**Build (A), per-operation locking, as the one protocol on every platform.
Make the daemon (B) an optional accelerator that is itself an (A) client,
and leave it off by default.**

- **(A) is the protocol.** Every process that touches the file, whether
  that's an MCP server, the CLI, a hook, `inspect`, the Python binding or a
  phone app, keeps the file closed between calls. It takes an OS lock for
  each call (shared for reads, exclusive for writes), re-checks the header,
  catches up if another process committed, does the work, and commits
  before it lets go.
  - No new format is needed.
  - It is the only option on iOS and Android.
  - It closes the same parity rows as (B).
- **(B) never owns the file.** A `mnemo daemon` holds no lock between
  calls. It's simply the one long-lived (A) handle that stays warm, with a
  local socket in front of it.
  - Clients that find it send their calls over the socket, and clients that
    don't open the file themselves.
  - If it dies, nothing breaks. Each call falls back to the direct path,
    and the lock and the file are exactly as (A) left them.
  - That keeps readers like `inspect`, `export` and the phone working
    without the daemon, and it means there is one locking protocol to
    test, not two.
- **The default** for `mnemo serve --mcp` becomes `--shared`, which is (A),
  after one release behind the flag. Today's lifetime lock stays available
  as `--exclusive`. The daemon comes later, and only if the dogfood runs
  show the catch-up cost hurting (100K-memory brains with frequent writes
  from other processes), or when `mnemo watch` (13.1b) or background sync
  (14.1) needs a long-lived process anyway.
- **Before any (A) code,** two existing gaps must be fixed. Both are
  explained below ("Gaps in today's code").
  - `compact_file` releases its lock before it renames the new file into
    place.
  - A handle can't tell that the file at its path was replaced.

Why not (B) as the base: a daemon that owns the file makes every other
reader depend on it. Under that design `inspect`, `export --git`, the CLI
fallback and the phone need either the daemon or a second protocol. And
the daemon doesn't run on mobile, which needs (A) anyway.

## The problem today

Every read-write open holds an exclusive `flock` (Unix) or `LockFileEx`
(Windows) lock for the handle's lifetime (`store/load.rs:open_with_lock`).
A read-only open takes a shared lock, which the OS refuses while an
exclusive lock is held.

So while one MCP server runs:
- a second session's server gets `Locked`;
- so do a hook's `mnemo recall` and the CLI's read commands;
- `inspect` gets "a writer has this file open".

## (A) Per-operation locking

### The protocol

A shared handle (`Mnemo::open_shared`, Python `open(..., shared=True)`,
`serve --mcp --shared`) keeps these between calls:
- its secret (zeroized on drop), the unwrapped data key, and the KDF
  parameters;
- the decoded state: catalog, index, cache directory, free list, vector
  column and page cache;
- the **stamp** of the state it holds: the file identity (`dev`/`ino` on
  Unix, the volume serial and file ID on Windows), the header's
  `write_counter`, and the committed transaction id.

It holds **no file descriptor and no lock** between calls.

Each call:

1. **Do the slow work first, unlocked.** Embedding a text (an external
   process) and building the query vector happen before the lock is taken.
   Nothing slow ever runs inside the lock.
2. **Open the path** (`open(2)` with close-on-exec, about 10 µs). The
   descriptor is wrapped in `LockedFile`, so it is **unlocked explicitly
   before it closes** (FLAKE-1, below).
3. **Take the lock with bounded backoff**: shared for reads, exclusive for
   writes. Use `try_lock` in a loop with jittered sleeps (1 ms, doubling to
   50 ms) until a deadline (default 10 s, settable per handle; `--wait` on
   the CLI). Past the deadline the call fails with `Locked`, saying who is
   likely holding the file (see "Long operations"). It never blocks without
   a deadline, the same rule as 10b.2.
4. **Check identity.** `fstat` the descriptor and `stat` the path. If they
   differ, the file was replaced between the open and the lock (a
   compaction): drop the lock and go back to step 2. If the identity
   differs from the stamp, the file was replaced since the last call, so
   reload from scratch with the kept secret (one KDF run).
5. **Check staleness.** Read page 0, verify its seal under the data key, and
   compare `write_counter` and the committed transaction id with the stamp.
   - **Equal:** the in-memory state is current. This is the common case,
     and it costs one 8 KiB read and one GCM check.
   - **Different:** another process committed. **Catch up** (below), then
     continue.
6. **Check for a pending WAL.** If the WAL holds a committed transaction
   that hasn't been checkpointed (a writer crashed mid-commit), a shared
   holder drops its lock and takes the exclusive one. It then re-checks
   from step 4, replays the WAL as `open` does today, and goes on. The lock
   can't be converted atomically (`flock` says so), hence the re-check.
   - A handle opened read-only (`inspect`, `--no-track`) never replays.
     It fails with today's `NeedsWriteOpen`, and the next writer's call
     recovers the file.
7. **Run the call.** A mutation **commits before the lock is released**:
   WAL commit, data pages, header, sync, which is what the MCP server
   already does after every mutation (`mcp.rs`). The stamp is updated from
   the new header.
8. **Unlock, then close** (`LockedFile`).

A read holds the shared lock for the length of the read. A write holds the
exclusive lock for one durable commit, about 16 ms with 3 fsyncs on the M1
Pro (`device_budget_v0_11_0`). Several readers run at once. Writers queue,
so across all processes one file takes roughly 60 durable commits a second.
That is far above what agents write (a few times a minute each).

### Catching up after another process's commit

- **First version: reload.** Rebuild the control plane exactly as `open`
  does, minus the KDF. Clear the page cache. v9 binds each page's
  generation into its AAD, so a stale cached page that was freed and
  reused fails its GCM check rather than returning wrong data. A
  mismatch is a bug, not a silent wrong answer.
- **Later: incremental catch-up.** v9 writes catalog and index changes as
  delta chains tagged with the writing transaction. A handle at
  transaction *t* applies only the deltas newer than *t*, keeps the
  resident vector column (adding the new facts' vectors, dropping deleted
  and superseded ones), and keeps the page cache except for pages the
  free list shows as reused. This is what makes (A) cheap at 100K. Build
  it behind the plain reload, with a test that both give the same state,
  and measure it (a PERF-2 cell).

### Writes that only this handle makes: access statistics and buffering

- **Recall statistics.** A recall with `track_access` dirties the catalog
  (`store/recall.rs`), so a shared recall would need the exclusive lock and
  a commit. Instead, a shared handle keeps the bumps as a commutative delta
  (`id → +count, max accessed_at`) and applies them at its next exclusive
  window, or at `close`, on top of whatever state it caught up to. A recall
  stays a shared-lock read. If the process dies first, the bumps are lost,
  which is acceptable for statistics.
- **No commit coalescing in shared mode.** The mobile stores' coalesced
  commits (MOBILE-2) hold writes in memory across calls. Applying them
  after another process committed would mean replaying operations, not
  pages. In shared mode each mutation commits, as the MCP server already
  does. A `Session`'s turns are mutations like any other.

### Long operations

`compact`, `rekey --rotate`, `build_index` at 100K and a large `import`
hold the exclusive lock for seconds. To make the resulting
`Locked` say why, the holder writes one line to a sidecar file before
taking the lock and removes it after:
`<file>.mnemo-lock-info`, holding the operation, pid, start time and tool.
A waiter that reaches its deadline reports that line, for example
"compacting since 12:01 (pid 4242)". The sidecar is a hint only: a stale
one (a pid that no longer exists) is ignored. The lock itself is the only
arbiter.

### Crash cases

| What dies, and when | What the others see | Recovery |
|---|---|---|
| A reader, while holding the shared lock | The kernel releases the lock when the process exits | Nothing to do |
| A writer, before its WAL commit | Lock released; the header is unchanged | Nothing was committed; the stamp check sees no change |
| A writer, after its WAL commit and before the header write | Lock released; a pending WAL | The next caller's step 6: it takes the exclusive lock and replays, as `open` does today. A read-only caller gets `NeedsWriteOpen` until a writer's call |
| A writer, with the header torn mid-write | Lock released | The torn-header scan already picks the newest commit that validates (`open.rs`); unchanged |
| A process that is stopped (`SIGSTOP`, a debugger, a sleeping laptop, a hung disk) while it holds the lock | Callers wait until their deadline, then get `Locked` with the lock-info line | The holder resumes or is killed. Nothing ever hangs |
| A process that spawned a child while it held a lock, then died or dropped the handle | Without the explicit unlock, the child's copy of the descriptor would keep the lock until it `exec`s | FLAKE-1's explicit unlock in `LockedFile` (below) |
| The MCP server is killed between calls | Nothing: it holds no lock between calls | None |

### FLAKE-1 is the baseline for every lock path

An `flock` belongs to the open file description, not to a descriptor. Agent
apps spawn child processes constantly. Between `fork` and `exec`, a child
holds a copy of the parent's file table, and close-on-exec only acts at the
`exec`. v0.12.3 fixed the resulting `Locked` by unlocking explicitly in
`LockedFile::drop` (`pager.rs`), which releases the lock whatever copies
exist.

(A) takes and releases locks far more often, on every call, so this
window opens far more often. Two rules follow:
- **every lock 12.4 takes goes through `LockedFile`**: the per-call file
  lock, the presence locks (below), and any sidecar lock;
- **the tests include FLAKE-1's pattern for each:** a thread spawning
  children in a loop while another thread runs shared calls, and a second
  process asserting that it is never refused.

Windows handles aren't inherited unless asked for, so the explicit unlock
is harmless there.

### Things (A) refuses

- **Network and synced folders.** `flock` over NFS and SMB is unreliable,
  and a cloud-sync folder copies the file underneath the lock (this
  project's iCloud `name 2.ext` copies). `open_shared` checks the
  filesystem (`statfs` `MNT_LOCAL` on macOS, the magic numbers on Linux,
  `GetDriveType` on Windows) and refuses a non-local one, unless the caller
  passes `allow_network_fs`. It can't detect a sync client on a local disk,
  so the docs say not to put a shared brain in a synced folder (13.7's
  merge is the answer for copies).
- **Mixed versions.** An older `mnemo` (or `--exclusive`) holds the lock for
  its lifetime. Shared callers then wait and get `Locked` naming it. That's
  safe and loud, just not concurrent. No version can corrupt another's
  file, because both use the same OS lock.

## (B) The daemon, as an (A) client

- **What it is.** `mnemo daemon --file <brain>` is one long-lived shared
  handle with a local socket in front of it. It speaks the MCP tool set
  plus a few internal calls (stat, inbox wait, dump for `inspect`).
- **What it isn't.** It never holds the lock between calls, and it isn't
  required for any call to work.
- **Discovery.** A client hashes the file's identity (`dev`/`ino`, not the
  path, so hard links and symlinks agree) and looks for:
  - `$XDG_RUNTIME_DIR/mnemo/<hash>.sock` on Linux;
  - `$TMPDIR/mnemo-<uid>/<hash>.sock` on macOS (a socket path must stay
    under 104 bytes);
  - the named pipe `\\.\pipe\mnemo-<sid>-<hash>` on Windows.

  The directory is 0700, and the server checks the peer's uid
  (`SO_PEERCRED` / `getpeereid`; a pipe ACL on Windows). On connect, a
  version handshake. Any failure means the client opens the file itself.
- **The trust boundary changes, and the docs must say so.** While the
  daemon runs, any process running as the same user can read and write the
  brain through the socket without the passphrase. That's the ssh-agent
  model. Today such a process also needs the secret, though it can usually
  find it (the MCP config holds it in plain text until 12.3). This is why
  the daemon is opt-in.
- **Group commit.** Writes that arrive together share one commit (a batch
  of 100 costs 20 to 37 ms against 16 ms for one). That's (B)'s real
  throughput advantage, and it only matters with many writers.
- **Crash.** Clients see EOF and retry the call directly. The file is in
  whatever state (A) leaves after a crash (the table above). A call that
  was mid-flight when the daemon died is reported as failed, never retried
  silently, because it may have committed.
- **Lifecycle.** It starts explicitly (`mnemo daemon start`), or under
  `mnemo watch`. It stops after an idle period (default 30 minutes, as
  with `inspect`). It is never auto-spawned by a plain CLI call. It
  re-reads nothing from the environment after start.

## Comparison

| | (A) per-operation locking | (B) daemon (on top of A) |
|---|---|---|
| Concurrent agents | Dozens of readers at once; writers queue at about 16 ms each, about 60 commits a second per file. The weak spot: every call after another process's commit pays a catch-up | Dozens; one warm state, no catch-up between its own clients, group commit |
| Per-call cost when nobody else wrote | open, lock, an 8 KiB read and a seal check (not measured; well under the 0.4 ms of a whole raw-key open at 1K) | The same check inside the daemon, plus a local socket round trip (not measured) |
| Per-call cost after another process's commit (full reload) | 10K: 3.2 ms reload + 8.8 ms first recall. 100K: 29.7 ms + 112.5 ms. Incremental catch-up should cut most of it (to be measured) | None for the daemon's own clients; a direct opener pays the (A) cost |
| A fresh process (hook, CLI) | Adds the KDF: secure-KDF open 16.9 ms against 2.9 ms with a raw key at 10K (44.2 against 30.1 ms at 100K) | The socket call skips the open and the KDF entirely |
| Crash behaviour | The kernel drops locks; WAL replay on the next writer; FLAKE-1 rule | The same for the file; clients fall back. One more process that can crash, but nothing depends on it |
| Readers (`inspect`, CLI reads) | Work alongside writers; wait milliseconds at most | The same (direct), or over the socket |
| 13.1 queue, 13.3 claims | The claim compare-and-set runs inside an exclusive window | The same code, running in the daemon |
| 13.1b wake-ups | Each session's MCP server watches the file and checks its own inbox (below) | The daemon sees every commit made through it, and still watches for direct ones; it pushes to the connected servers |
| 14.1 background sync | Needs a long-lived process: `mnemo watch` or a scheduled job | The natural home |
| Mobile | Required; fits MOBILE-2 (below) | Not available |
| Security boundary | Every process needs the secret | Same user = access while it runs |
| Format change | None | None |

### The numbers

Sources, all on the M1 Pro:
- `test/scripts/perf_v0.5.0.json`, `device_budget_v0_11_0` (v9 files,
  384 dimensions, 300-byte texts, fast KDF unless noted);
- the raw-key cells;
- PLAN.md's MEM-1 cells for v8.

No new measurement was needed for this note. The two "not measured" cells
above are the first things 12.4's bench adds.

| v9 | 10K | 100K |
|---|---|---|
| Open, fast KDF (the reload cost) | 3.22 ms | 29.66 ms |
| Open, raw key | 2.90 ms | 30.10 ms |
| Open, secure KDF | 16.94 ms | 44.22 ms |
| First recall on a fresh handle (loads the vector column) | 8.77 ms | 112.5 ms |
| Warm recall (the daemon's warm call, before the socket) | 2.20 ms | 2.47 ms |
| One durable write | 14.8 ms | 16.1 ms |
| A batch of 100 writes | 19.95 ms | 36.6 ms |

MEM-1's "232 ms to open an indexed 100K file" is the v8 number. v9 opens
the same corpus in about 30 ms, but its first recall loads the resident
fp16 column, about 112 ms at 100K. Below 20K facts (`V9_ANN_MIN_FACTS`)
there is no ANN index.

**So:** at 10K, a full reload plus first recall is about 12 ms, which (A)
can pay on every call where another process wrote. At 100K it's about
142 ms, which (A) can pay occasionally but not on every call, so the
incremental catch-up is the work that makes (A) good there. For hooks,
the bigger cost is the KDF on every fresh process (about 14 ms extra). 12.3's
keychain raw key removes it under (A); the daemon removes it under (B).

## Claims and presence

These are designed here and shipped as API in 13.3. Both use the lock and
staleness machinery above.

### Presence: liveness from locks, activity from commits

The spec says presence is a heartbeat record "at most once a minute,
piggybacked on a commit". It splits into two signals, because a heartbeat
that commits on its own would cost a durable write per agent per minute.
That's about 57 KB of file growth per single write in v9, plus a snapshot
per commit, which would push real restore points out of the 24-hour
retention window.

- **`alive` (free, exact).** Each shared handle that declares an agent id
  holds a shared lock on its own sidecar file for its lifetime:
  `<file>.presence/<hash of agent id>.lock`, in a 0700 directory, through
  `LockedFile`. To ask "is X alive?", try an exclusive lock on X's file
  without waiting.
  - Acquired: X's process is gone. The kernel released it, even after a
    `kill -9`.
  - Refused: X's process is running.

  No writes to the brain, and nothing goes stale.
- **`last_active` (piggybacked).** The `_mnemo.kind = "presence"` record
  (agent id, role, tool, `last_active`) is updated only inside a commit the
  agent makes anyway, at most once a minute. It answers "alive but idle for
  three hours", which is what "out of usage" looks like (the session's
  server is still running, but nothing happens).
- **`who()`** returns both, for each known agent.

### Claims: compare-and-set inside the exclusive window

- **The record.** A claim is a `_mnemo.kind = "claim"` record: topic,
  holder (agent id), `expires_at` (wall clock), and a `lease` in seconds.
- **`claim(topic, ttl)`** runs in one exclusive window: catch up, read the
  live claim for the topic, and decide.
  - The topic is free if there is no claim, or the claim has lapsed: it's
    past `expires_at`, or its holder isn't `alive` by the lock probe.
  - If it's free, write ours and commit, and return `Claimed`.
  - Otherwise return `HeldBy { agent, expires_at }`.

  Two processes can't both win, because the second one's window starts
  after the first one's commit, and its catch-up sees that claim.
- **`renew` and `release`** run in the same kind of window.
- **Lapsing.** A crashed holder's claim lapses at once (the lock probe says
  it isn't alive). A stuck holder's lapses at `expires_at`. Nothing ever
  waits for a dead agent.
- **The clock.** It's one machine, so one clock, and wall-clock times
  survive a reboot. A claim taken just before a laptop sleeps simply
  expires.

**Keyed records, not new types.** Claims and presence are ordinary keyed
records (12.1), with slot `claim:<topic>` or `presence:<agent>` and the
shared scope. Supersession gives each its history. `export --git` leaves
them out (R-006.2 (d)).

**Tests,** with the spec's three, plus:
- two processes race for one claim 1,000 times: exactly one wins each time;
- a holder is killed mid-claim: the other process gets the claim at once
  through the lock probe, and at `expires_at` with the probe disabled;
- every wait has a deadline;
- the FLAKE-1 pattern on the presence locks.

## 13.1b wake-ups under each option

A wake-up needs something that sees every commit and can reach every
session.

- **Under (A),** each session's `serve --mcp --shared` watches the file:
  kqueue `EVFILT_VNODE`/`NOTE_WRITE` on macOS, inotify `IN_MODIFY` on
  Linux, `ReadDirectoryChangesW` on Windows, with a slow poll of the header
  stamp (every 30 s) as a safety net.
  - **On a change,** it waits briefly (debounce), takes the shared lock,
    and checks the stamp. Only if the stamp moved does it query its own
    role's inbox for `sent` items.
  - **For each one,** it pushes a channel event, or a
    `notifications/resources/updated` (13.1b), and marks it `delivered`
    in one exclusive window.

  The cost is one header check per foreign commit per session, and nothing
  while the file is quiet. The delivery state stays the source of truth,
  so a missed event loses nothing: the next turn's hook sees the item.
- **Under (B),** the daemon knows of commits made through it without
  watching, and it holds the connections, so it pushes to the right
  session's server directly. It still watches for direct writers.
- **`mnemo watch`**, which starts a session when work arrives for a role
  with none open, is a long-lived process under either option. It's the
  natural host for the daemon later.

The guardrails (rate limits, hop cap, kill switch) live in the code that
marks items `delivered`, so they're the same under both options.

## Readers: `inspect` and the CLI's read commands

| | Today | Under (A) | Under (B) |
|---|---|---|---|
| `inspect` | Opens read-only, reads everything, closes (`inspect.rs`), so it never holds a lock while serving. Gets `Locked` while any writer is open | The same code. With writers holding locks only per call, the read-only open waits milliseconds (bounded backoff instead of today's immediate `try_lock` failure). A crashed writer's pending WAL gives `NeedsWriteOpen` ("any writer's next call recovers it"); `inspect` never writes | The same, direct. Optionally `/api/reload` asks the daemon for a dump, to skip the KDF on each reload |
| CLI reads (`info`, `list`, `recall --no-track`, `export`, `verify`) | `open_read_only` and `try_lock`: `Locked` while a writer is open | Wait with a deadline (`--wait`, default 10 s), then run alongside other readers | Use the socket when a daemon answers, else direct |
| CLI writes (`remember`, `update`, `compact`) | `Locked` while an MCP server is open | One exclusive window each; `compact` as below | Through the daemon if present (`compact` goes direct, see below) |
| A hook (`recall` at session start) | `Locked` while the session's MCP server is open | Works; pays the KDF per process unless 12.3's raw key is in the keychain | Works; no KDF |

## Worktrees (R-006.2 (a))

- **The path.** The default brain path resolves through
  `git rev-parse --git-common-dir`, so every worktree of a repository
  names the same file.
- **The lock (A)** is on that file itself, so worktrees need nothing more.
  Hard links and symlinks also agree, because `flock` is per inode.
- **The sidecars** (`.mnemo-lock-info`, `.presence/`) live next to the
  brain, inside the common git directory, never in a worktree. A
  worktree's removal touches none of them.
- **The daemon's socket (B)** is keyed by the file's identity, not its
  path, and lives in the per-user runtime directory, not in the repository.
  So all worktrees (and any other path to the same file) reach one daemon.
- **A `--personal` brain** (R-006.2 (e)) is a second file with its own lock,
  sidecars and (optional) daemon. A session can hold shared handles on
  both.

## Mobile (MOBILE-2)

iOS and Android can't run a daemon, so (A) must stand alone there, and it
does.
- **iOS.** The reason for MOBILE-2's background rules is that iOS kills a
  suspended app holding a file lock in a shared container (`0xdead10cc`).
  A shared-mode store holds no lock between calls, so suspension between
  calls is always safe. Today's "while inactive, reopen, work, flush and
  close inside an expiring background activity" becomes "lock, work,
  commit, unlock inside the activity". The reopen (and its few
  milliseconds) goes away; the activity wrapper stays.
- **The real multi-process case on phones** is an app and its extensions
  (a share extension, a widget, a notification service) on one App Group
  file. Today the second store gets `Locked`. In shared mode they take
  turns per call.
- **The default stays as it is** for a single-process app (open
  exclusively, on iOS only while in the foreground; coalesced commits). Shared mode is
  opt-in for App Group files, because it gives up coalescing (above).
- **Android.** The file stays open today because Android doesn't kill for
  a held lock. Shared mode is opt-in for the same multi-process cases.

## Format

**Neither option needs a format change.** The stamp uses fields every v9
header already has and seals:
- `write_counter`, sealed since v7;
- the committed transaction id;
- the file's identity, from the filesystem.

Incremental catch-up uses v9's existing generation-tagged delta chains.
Claims and presence are `_mnemo.*` metadata on ordinary records. The
sidecar files and the socket are outside the brain.

Shared mode is v9-only: a v8 file opens read-only, as today. If
implementation finds it does need a header field, that goes through the
format-version policy (AGENTS.md) with its own design check. Nothing here
expects it to.

## Gaps in today's code that 12.4 must fix first

1. **`compact_file` drops its lock before the rename.** `compact_file_secret`
   (`store/maintenance.rs`) runs `drop(old)` and then
   `rename(tmp, path)`. A process that opens the file in that window gets
   the old inode, and its writes are lost when the rename replaces it.
   - Today the window is microseconds wide. In shared mode every
     long-lived handle would keep writing to the old inode, so it is
     always open.
   - **Fix:** on Unix, hold the old file's exclusive lock through the
     rename and the directory sync; the identity check (protocol step 4)
     sends waiters to the new file. On Windows, the existing comment says
     a rename over an open file fails. Test that on the Windows CI leg
     first; if it holds, Windows keeps a microsecond window that the
     identity check narrows but can't close, and the docs say so.
   - The same applies to `rekey --rotate` and the `.compact-tmp` name,
     which two concurrent compactions would share. Use a unique temp
     name.
2. **A handle can't tell the file was replaced.** The stamp's identity
   check (step 4) closes this.
   - After a rotation the data key is new, and the kept secret reopens the
     file (one KDF run).
   - If the secret changed too (`rekey` then `compact`), the reopen fails
     with `WrongPassphrase`. That's the right result: rotation revokes
     running sessions that only know the old secret.
   - A plain `rekey` (no rotation) keeps the data key, so running handles
     keep working. That matches today's documented property that `rekey`
     alone doesn't revoke a data key someone already has.
3. **`try_lock` with no wait** in `open_with_lock` becomes the bounded
   backoff for shared and read-only opens. Exclusive opens keep failing at
   once, as today, so existing callers keep their behaviour.

| AGENTS.md role rules → loaded at every session start (12.2) | **Enables it:** the SessionStart hook can read while servers run | The same, without the KDF per hook |
| WORKLOG (DISPATCH, READY, ...) → tasks and messages per role | Enables it (needs 13.1) | The same |
| The git backup of PLAN.md → `mnemo export --git` | Enables it alongside live sessions | The same |
| `SECURITY.local.md` → a separate private brain | Enables it (two shared handles per session) | The same |
| PLAN.md Status and specs; reviewer_notes.md | Not 12.4's rows (12.1, 12.7, 13.x) | |
| Reading PLAN.md on the phone | Not 12.4 (INSP-1, Phase 15) | |

Both options close or enable the same rows. They differ only in cost at
scale and in the trust boundary, which is why (A) is the base and (B) is
optional.

## Implementation order (after sign-off)

1. **Fix the gaps** (compaction rename, identity check, a unique temp name),
   with a test that a write racing a compaction is never lost.
2. **The lock layer:** `open_shared` with full-reload catch-up, the
   bounded backoff, the access-statistics delta, and the lock-info
   sidecar.
3. **The tests:**
   - two processes interleaving remember, update, recall and cache_put,
     with crash injection at every write (the `__failpoints` hook in a
     child process);
   - the proptest model extended with a second handle;
   - the FLAKE-1 pattern;
   - every wait with a deadline;
   - Windows on CI.
4. **Surfaces:** Python `shared=True`; `serve --mcp --shared`; waiting CLI
   reads; `inspect` waiting instead of failing.
5. **The bench:** the unchanged-header check, the full-reload catch-up
   cost, two and eight processes at 10K and 100K.
6. **Incremental catch-up,** measured against step 5.
7. **Presence locks and the claim compare-and-set** (the engine half of
   13.3), with the claim tests.
8. **Shared becomes the default** for `serve --mcp` one release later.
9. **The daemon,** only if step 5 or 6's numbers or `mnemo watch` call for
   it.
