## Recommendation

**Build (A), per-operation locking, as the one protocol on every platform.
Make the daemon (B) an optional accelerator that is itself an (A) client,
and leave it off by default.** RB-006 found nothing that argues for (B)
as the base, and nothing that needs a format change.

- **(A) is the protocol.** Every process that touches the file, whether
  that's an MCP server, the CLI, a hook, `inspect`, the Python binding or a
  phone app, keeps the file closed between calls. It takes an OS lock for
  each call (shared for reads, exclusive for writes), re-checks the header,
  catches up if another process committed, does the work, and commits
  before it lets go.
  - No new format is needed.
  - It is the only option on iOS and Android.
  - It closes the same parity rows as (B).
- **(B) never owns the file.** A `mnemo daemon` holds no lock between
  calls. It's simply the one long-lived (A) handle that stays warm, with a
  local socket in front of it.
  - Clients that find it send their calls over the socket, and clients that
    don't open the file themselves.
  - If it dies, nothing breaks. Each call falls back to the direct path,
    and the lock and the file are exactly as (A) left them.
  - That keeps readers like `inspect`, `export` and the phone working
    without the daemon, and it means there is one locking protocol to
    test, not two.
- **The default** for `mnemo serve --mcp` becomes `--shared`, which is (A),
  after one release behind the flag. Today's lifetime lock stays available
  as `--exclusive`. The daemon comes later, and only if the dogfood runs
  show the catch-up cost hurting (100K-memory brains with frequent writes
  from other processes), or when `mnemo watch` (13.1b) or background sync
  (14.1) needs a long-lived process anyway.
- **The two gaps in today's code are fixed** in v0.14.0 step 1 (since
  RB-006; see "Gaps in today's code").

Why not (B) as the base: a daemon that owns the file makes every other
reader depend on it. Under that design `inspect`, `export --git`, the CLI
fallback and the phone need either the daemon or a second protocol. And
the daemon doesn't run on mobile, which needs (A) anyway.

## The problem today

Every read-write open holds an exclusive `flock` (Unix) or `LockFileEx`
(Windows) lock for the handle's lifetime (`store/load.rs:open_with_lock`).
A read-only open takes a shared lock, which the OS refuses while an
exclusive lock is held.

So while one MCP server runs:
- a second session's server gets `Locked`;
- so do a hook's `mnemo recall` and the CLI's read commands;
- `inspect` gets "a writer has this file open".

## (A) Per-operation locking

### The protocol (since RB-006)

A shared handle (`Mnemo::open_shared`, Python `open(..., shared=True)`,
`serve --mcp --shared`) keeps these between calls:
- **its secret** (zeroized on drop), the unwrapped data key, and the KDF
  parameters. It needs the secret because every compaction gives the file
  a new data key (see "The trust boundary");
- the decoded state: catalog, index, cache directory, free list, vector
  column and page cache, and its per-handle settings and embedder;
- **the stamp** of the state it holds:
  - the file identity (`dev`/`ino` on Unix, the volume serial and file ID
    on Windows), as the quick first test;
  - **the header's seal**: its 12-byte nonce and 16-byte tag, 28 bytes
    compared. The seal gets a fresh random nonce on every header write
    (`format.rs`), so unlike the counters it can't repeat across
    compactions, copies written over the file, or restores. It needs no
    format change.
  - The stamp can also be **cleared**, which means "reload from the file
    at the next call, whatever page 0 says" (protocol step 7).

Between calls it holds **no lock and no descriptor on the brain**, with two
exceptions:
- the presence lock on its sidecar file, if it declared an agent id (see
  "Claims and presence"; not on iOS, see "Mobile");
- the 13.1b watcher's descriptor, if it watches (see "13.1b wake-ups"),
  which holds no lock.

**Each call has one deadline** (default 10 s, settable per handle; `--wait`
on the CLI; hooks pass 2 s). It covers both locks and protocol step 4's retries.

**Each call can be cancelled** from another thread (an iOS background
activity's expiry handler, say). A cancelled call releases every lock it
holds and returns `Cancelled`. The mobile stores pass a deadline no longer
than the activity's remaining time.

Each call:

1. **Do the slow work first, unlocked.** Embedding a text (an external
   process) and building the query vector happen before the lock is taken.
   Nothing slow ever runs inside the lock.
2. **Open the path, without creating it** (`open(2)` with close-on-exec,
   about 10 µs). A missing file is an error, never a new empty brain (a
   `git clean -fdx` on an ignored brain, say). The descriptor is wrapped
   in `LockedFile`, so it is **unlocked explicitly before it closes**
   (FLAKE-1, below).
3. **Take the lock with writer preference** (see "Writer preference"):
   shared for reads, exclusive for writes. `try_lock` in a loop with
   jittered sleeps, until the call's deadline, or a cancel. Past the
   deadline the call fails with `Locked`, saying who is likely holding the
   file (see "Long operations"). It never blocks without a deadline, the
   same rule as 10b.2.
4. **Check identity.** `fstat` the descriptor and `stat` the path.
   - If they differ, the file was replaced between the open and the lock
     (a compaction): drop the lock and go back to protocol step 2, within
     the same deadline. (v0.14.0 step 1's `open_with_lock` does this today,
     for 8 attempts.)
   - If the identity differs from the stamp, the file was replaced since
     the last call: reload from scratch with the kept secret (one KDF run).
5. **Check staleness.** Read page 0 and compare its seal with the stamp.
   There are three outcomes:
   - **Equal:** the in-memory state is current. This is the common case:
     one 8 KiB read, a 28-byte compare, and the WAL check in protocol step 6.
   - **Different, and it verifies under the held data key:** another
     process committed. **Catch up** (below), then continue.
   - **It doesn't verify under the held key:** treat the file as replaced.
     Every compaction makes a new data key, and on filesystems that reuse
     inode numbers the identity check can miss it. Reopen with the kept
     secret (one KDF run). Only if that fails, return the specific error:
     `WrongPassphrase` when the secret no longer opens the key, or
     `HeaderTampered` when it opens the key but the seal still fails.
   - **A torn page 0** isn't healed under a shared lock: the scan reads the
     whole file and runs the KDF per candidate (`open.rs`). A read-write
     caller takes the exclusive lock and runs `open`'s recovery; a
     read-only caller gets `NeedsWriteOpen` at once, without the scan.
6. **Check for a pending WAL** (one 29-byte read, `wal.rs`). If the WAL
   holds a committed transaction that hasn't been checkpointed (a writer
   crashed or failed mid-commit):
   - A shared holder drops its lock and takes the exclusive one. It
     re-checks from protocol step 4, replays the WAL as `open` does today, and then
     **always reloads**: the replay rewrote page 0 with a later transaction
     than the handle's state. The lock can't be converted atomically
     (`flock` says so), hence the re-check.
   - A handle opened read-only (`inspect`, `--no-track`) never replays. It
     fails with today's `NeedsWriteOpen`. To keep that state short when
     only readers are active, `serve --mcp --shared` and the 13.1b watcher
     heal the file when they see it.
7. **Run the call.** For a mutation:
   - **Clear the stamp first,** before the mutation touches the handle's
     memory. It's set again only from the header a successful commit
     wrote. An error, or a panic inside the window (which unlocks through
     `LockedFile::drop`), leaves it cleared, so the next call reloads.
     That way a handle is never ahead of the file with a stamp that says
     "equal".
   - **Take a fresh generation lease** for the window: the header-only
     transaction that `ensure_gen_lease` commits today once per handle
     (`records.rs`) is taken in every exclusive window that writes, and
     `gen_leased` resets when the lock is released. Every page a writer
     seals then carries a generation no other writer has used, even when
     sessions interleave and one fails before its commit. It costs two
     more fsyncs a write (3 to 5); step 5's bench measures it.
   - **Commit before the lock is released:** WAL commit, data pages,
     header, sync, which is what the MCP server already does after every
     mutation (`mcp.rs`).
   - **A failure before the WAL's commit point** returns the error, and
     nothing was stored.
   - **A failure after the commit point** must not return a plain failure,
     because the next writer to open the file replays it. The call
     finishes the checkpoint from the WAL itself (it's the same replay),
     and returns `Ok` if that works. If it can't, it returns a distinct
     error saying the write **may have been stored**
     (`MnemoError::MaybeStored`), so a caller doesn't retry a write that
     is already in.
8. **Check identity again after a commit.** If the path no longer names
   the file just written (an older compactor renamed over it during the
   commit; see "Things (A) refuses"), return a distinct error saying the
   file was replaced during the write and the write isn't in the file at
   the path. That turns a silent loss into a reported one.
9. **Unlock, then close** (`LockedFile`).

### Writer preference (since RB-006)

`flock` has no fairness. With dozens of readers taking shared locks back to
back, a writer's `try_lock_exclusive` can keep failing until its deadline.
REVIEWER-B's simulation confirmed it (8 of 40 commits got in against eight
readers, none against sixteen). So writers announce themselves through an
**intent lock**: the file `intent.lock` in the sidecar directory (see
"Sidecar files").

- **A writer** takes the intent lock exclusively, then the main lock
  exclusively, both within the call's one deadline. It releases the intent
  lock as soon as it holds the main one. Other writers queue on the intent
  lock.
- **A reader** takes the intent lock shared, **tries the main lock once**
  without waiting, and releases the intent lock whether or not it got the
  main one. If it didn't, it sleeps and starts again from the intent lock.
  So a reader never holds the intent lock while it waits, and a long
  operation on the main lock can't keep a second writer from queueing.
- **While a writer waits** holding the intent lock, new readers can't get
  past the intent step. The readers already inside finish within one read,
  and the writer gets the main lock.
- **Both locks go through `LockedFile`.** A crashed writer's intent lock is
  released by the kernel like any other.
- **The test:** eight reader processes in tight loops, and one writer that
  still commits well within its deadline (asserted: every write under 1 s
  across 100 commits). Step 5 adds four and eight writers at once, asserted
  on the 99th percentile, and readers' waits. If several writers' 99th
  percentile is poor, step 5 adds an order among writers.

**The throughput.** A read holds the shared lock for the length of the
read. A write holds the exclusive lock for one durable commit: about 16 ms
with 3 fsyncs on the M1 Pro (`device_budget_v0_11_0`), and more once the
generation lease adds two fsyncs. The backoff's sleeps overshoot a hold
that short. REVIEWER-B's simulation of the protocol gave about 33 commits a
second with several writers, and about 20 with readers present, not the 60
this note first said. So until step 5 measures the engine, say **tens of
commits a second** per file, and readers waiting tens to hundreds of
milliseconds while a writer is busy. That is still far above what agents
write (a few times a minute each). Step 5 also tries short sleeps while a
wait is young (a few milliseconds), growing only after.

### Catching up after another process's commit (since RB-006)

- **First version: reload.** Rebuild the control plane exactly as `open`
  does, minus the KDF, and **clear the page cache**. Clearing it is what
  makes this safe: the cache holds decrypted pages keyed by page number
  alone, and a hit returns before any decryption (`pager.rs`). So v9's
  generation in the AAD protects pages read from disk, **not** cached
  pages. Keep the handle's per-handle settings and its embedder across the
  reload (a plain `open` resets them).
- **Later (step 6): incremental catch-up.** v9 writes catalog and index
  changes as delta chains tagged with the writing transaction. A handle at
  transaction *t* applies only the deltas newer than *t* and keeps the
  resident vector column (adding the new facts' vectors, dropping deleted
  and superseded ones). It may keep its page cache only if the cache is
  keyed by page number and generation, or if it drops every cached page a
  changed row names (old and new location). The free list can't tell it
  which pages were reused. It falls back to the full reload whenever the
  chain doesn't reach back to *t* (a base rewrite happened). This is what
  makes (A) cheap at 100K. Build it behind the plain reload, with a test
  that both give the same state (including a base rewrite, a compaction of
  tombstones, and a page reused between the two points), and measure it (a
  PERF-2 cell).

### Writes that only this handle makes (since RB-006)

- **Access statistics.** Two reads write on a read-write handle today:
  - a recall with `track_access` dirties the catalog (`store/recall.rs`);
  - a cache hit (`cache_get`, `cache_get_semantic`) updates the cache
    directory's `accessed_at` and `access_count` and sets `dirty_cache`
    (`cache_api.rs`).

  In shared mode either would need the exclusive lock and a commit.
  Instead, a shared handle keeps both kinds of bump as a commutative delta
  (`id → +count, max accessed_at`). It applies them only with a commit it
  makes anyway, on top of whatever state it caught up to, and **drops them
  at `close`**: a close that needed the lock could wait out its deadline
  and fail, and each such commit would make every other process reload. A
  recall and a cache hit stay shared-lock reads. Bumps that never ride a
  commit are lost, which is acceptable for statistics.
- **Per-handle settings.** Some settings decide what a commit does to the
  whole file:
  - snapshot retention runs at every commit with the committing handle's
    `max_snapshots` (`snapshots.rs`);
  - the cache budgets;
  - `turn_compress_after`.

  In shared mode one process's explicit setting would act on every
  process's data at its next commit. **In v0.14, shared handles use the
  defaults and refuse an explicit setting** with a clear error
  (`set_max_snapshots` and the others, and a non-default `MnemoConfig`).
  Storing the policy in the file comes later.
- **No commit coalescing in shared mode.** The mobile stores' coalesced
  commits (MOBILE-2) hold writes in memory across calls. Applying them
  after another process committed would mean replaying operations, not
  pages. In shared mode each mutation commits, as the MCP server already
  does. A `Session`'s turns are mutations like any other.
- **At their steps** (not before step 2):
  - **The embedding.** Protocol step 1 computes it before the lock, so after
    catching up, check that the file's dimensions (and model, where
    recorded) still match, and recompute if not.
  - **Read, then write, across calls.** Say what `update` and `forget`
    return for an id another process superseded or deleted in between.
    Consider an expected-version argument later.

### Long operations (since RB-006)

`compact`, `rekey --rotate`, `build_index` at 100K and a large `import`
hold the exclusive lock for seconds. To make the resulting `Locked` say
why, the holder writes one line, the operation, pid, start time and tool,
to `lock-info` in the sidecar directory.
- It writes the line **after it holds the lock**, so a second long
  operation that is still waiting can't replace the holder's line. It
  removes the line before unlocking.
- It writes the line to a new exclusive temp name and renames it into
  place, never by opening `lock-info` to truncate it (see "Sidecar
  files").

A waiter that reaches its deadline reports that line, for example
"compacting since 12:01 (pid 4242)". The sidecar is a hint only: a stale
one (a pid that no longer exists) is ignored. The lock itself is the only
arbiter.

### Sidecar files (since RB-006)

All of 12.4's extra files for a brain `X` live in one directory next to
it, `X.mnemo-shared/` (0700):
- `intent.lock`, the writer-preference lock;
- `lock-info`, the long-operation line;
- `presence/<hash of agent id>.lock`, the liveness locks.

**Where.** `X` is the brain's path with symlinks resolved, so two paths
through a symlinked directory find one sidecar directory. Hard links aren't
covered: two hard links to one brain get two sidecar directories, and the
docs say so.

**Created and checked, never trusted by name.** The directory and its
files sit in a directory others may be able to create names in. So:
- The directory is created with `mkdir`, never "create if missing, else
  use".
- A directory that's already there is checked with `lstat`. It must be a
  real directory (not a symlink), owned by the caller, with no group or
  other access. If it isn't, the handle doesn't use it: it takes the main
  lock alone, without writer preference, presence or `lock-info`, and says
  so once.
- Files in it are opened relative to the directory's descriptor
  (`openat`), with `O_NOFOLLOW`, and with `O_EXCL` when they're new, so
  the directory that was checked is the one used and no name in it is
  followed elsewhere.
- `lock-info` is written by temp name and rename, never truncated in
  place.
- **Tests:** a directory owned by someone else, a symlinked directory, and
  a symlink at each fixed name.

**A directory the caller can't write.** A reader of another user's brain,
or of a brain in a read-only directory, can't create the sidecar. It takes
the main lock alone, as above.

**Deleting it.** While nothing runs, deleting the directory loses nothing,
and the next handle creates it again. While handles run, it loses their
presence (see "Claims and presence").

**Ignoring them.** The name is fixed so one `.gitignore` pattern matches
it, wherever the brain lives:

```gitignore
*.mnemo-shared/
```

For this repository, that means `test/project.mnemo.mnemo-shared/`. The
pattern goes into `.gitignore` when the code lands (PLANNER-A). The
daemon's socket isn't a sidecar: it lives in a per-user directory (see
(B)).

### Crash cases (since RB-006)

| What dies or fails, and when | What the others see | Recovery |
|---|---|---|
| A reader, while holding the shared lock | The kernel releases the lock when the process exits | Nothing to do |
| A writer, before its WAL commit | Lock released; the header is unchanged | Nothing was committed. The next writer's window takes a fresh generation lease, so the dead writer's sealed but uncommitted pages never match a later generation |
| A writer, after its WAL commit and before the header write | Lock released; a pending WAL | The next caller's protocol step 6: it takes the exclusive lock, replays, and reloads. A read-only caller gets `NeedsWriteOpen` until a write-capable call or the watcher heals it |
| A writer, with the header torn mid-write | Lock released | A read-write caller runs `open`'s torn-header recovery under the exclusive lock; a read-only caller gets `NeedsWriteOpen` (protocol step 5) |
| **A commit fails before the commit point, and the process lives on** | Lock released; the header is unchanged | The call returns the error and nothing was stored. The handle's stamp stays cleared, so its next call reloads; it never serves or commits the failed write later |
| **A commit fails after the commit point, and the process lives on** | Lock released; a pending WAL | The call finishes the checkpoint itself and returns `Ok`, or returns `MaybeStored`. Never a plain failure. Its stamp stays cleared until a commit succeeds |
| **A handle that was current replays a WAL** (another writer died after its commit point) | The file has moved on to the replayed transaction | It always reloads after the replay (protocol step 6) |
| A process that is stopped (`SIGSTOP`, a debugger, a sleeping laptop, a hung disk) while it holds the lock | Callers wait until their deadline, then get `Locked` with the lock-info line | The holder resumes or is killed. Nothing ever hangs |
| A process that spawned a child while it held a lock, then died or dropped the handle | Without the explicit unlock, the child's copy of the descriptor would keep the lock until it `exec`s | FLAKE-1's explicit unlock in `LockedFile` (below) |
| The MCP server is killed between calls | Nothing: it holds no lock on the brain between calls | None |

### FLAKE-1 is the baseline for every lock path

An `flock` belongs to the open file description, not to a descriptor. Agent
apps spawn child processes constantly. Between `fork` and `exec`, a child
holds a copy of the parent's file table, and close-on-exec only acts at the
`exec`. v0.12.3 fixed the resulting `Locked` by unlocking explicitly in
`LockedFile::drop` (`pager.rs`), which releases the lock whatever copies
exist.

(A) takes and releases locks far more often, on every call, so this
window opens far more often. Two rules follow:
- **every lock 12.4 takes goes through `LockedFile`**: the per-call file
  lock, the presence locks (below), and any sidecar lock;
- **the tests include FLAKE-1's pattern for each:** a thread spawning
  children in a loop while another thread runs shared calls, and a second
  process asserting that it is never refused.

Windows handles aren't inherited unless asked for, so the explicit unlock
is harmless there.

### Things (A) refuses (since RB-006)

- **Network and synced folders.** `flock` over NFS and SMB is unreliable,
  and a cloud-sync folder copies the file underneath the lock (this
  project's iCloud `name 2.ext` copies). `open_shared` checks the
  filesystem and refuses a non-local one, unless the caller passes
  `allow_network_fs`:
  - macOS: `statfs` `MNT_LOCAL`;
  - Windows: a UNC path, which is what a network share or a mapped
    network drive normally canonicalizes to. **A drive letter mapped to a
    network share may not be detected** (`GetDriveType` would see it, but
    it needs `unsafe`, which the engine forbids; a small helper outside the
    engine crate is a later candidate);
  - **Linux: an allow-list** of filesystem magic numbers, not a deny-list:
    ext4, xfs, btrfs, tmpfs, f2fs (most Android phones keep app data on
    it), overlayfs (how a container sees its own disk) and zfs. Everything
    else is refused, which covers NFS, SMB, FUSE, virtiofs and 9p. A brain
    shared between a host and a container or WSL is a likely setup for
    coding agents, and on those mounts a lock may not reach the other side.
    The docs say so. **Shared mode on overlayfs assumes Linux 4.19 or
    later**: before 4.19 a lock taken before a file's copy-up could land on
    the lower file, and another process would lock the upper one.
- **Synced folders on macOS.** `statfs` can't see iCloud Drive or a
  File Provider client, because they're local disks underneath, and this
  repository hit that (2026-11-12). So on macOS, `open_shared` also:
  - **refuses** (unless `allow_network_fs`) a path under
    `~/Library/Mobile Documents` (iCloud Drive) or
    `~/Library/CloudStorage` (Dropbox, OneDrive, Google Drive and other
    File Provider clients). It resolves symlinks first, so `~/Desktop` and
    `~/Documents` under "Desktop & Documents in iCloud" are caught where
    they really live;
  - **warns** when the file is iCloud-managed by the same test this project
    ran on 2026-11-12: `NSURLIsUbiquitousItemKey` on the file's URL.
    Calling Foundation from Rust (`objc2-foundation`, one resource-value
    read) is cheap, but it's a new dependency, so the implementation checks
    its size first. If it's too heavy, warn instead for any path under
    `~/Desktop` or `~/Documents`.
  - A folder named `*.nosync` reports as not managed, and passes, as
    `mnemo.nosync` does.

  Other platforms can't detect a sync client on a local disk, so the docs
  say not to put a shared brain in a synced folder (13.7's merge is the
  answer for copies).
- **Mixed versions.** An older `mnemo` (or `--exclusive`) that holds the
  lock for its lifetime only makes shared callers wait and get `Locked`
  naming it. That's safe and loud, just not concurrent. **One exception:**
  a pre-0.14 `mnemo compact` releases its lock before it renames (the gap
  step 1 fixed). Against a shared writer that is the one pair the lock
  doesn't serialize, so a write can be lost.
  - With step 1's identity check, REVIEWER-B saw no loss in 481
    compactions.
  - Protocol step 8's check after the commit reports the rest instead of losing
    them silently.
  - **The v0.14 upgrade notes say:** update every `mnemo` on the machine
    (CLIs, wheels in every virtualenv, apps built against older bindings)
    before using `--shared`.
  - Whether to gate older binaries by format version (the only gate they
    obey) is decided before step 8 makes shared the default.

## (B) The daemon, as an (A) client (since RB-006)

- **What it is.** `mnemo daemon --file <brain>` is one long-lived shared
  handle with a local socket in front of it. It speaks the MCP tool set
  plus a few internal calls (stat, inbox wait, dump for `inspect`).
- **What it isn't.** It never holds the lock between calls, and it isn't
  required for any call to work.
- **Group commit.** Writes that arrive together share one commit (a batch
  of 100 costs 20 to 37 ms against 16 ms for one). That's (B)'s real
  throughput advantage, and it only matters with many writers.
- **Crash.** Clients see EOF and retry the call directly. The file is in
  whatever state (A) leaves after a crash (the table above). A call that
  was mid-flight when the daemon died is reported as failed, never retried
  silently, because it may have committed.
- **Lifecycle.** It starts explicitly (`mnemo daemon start`), or under
  `mnemo watch`. It stops after an idle period (default 30 minutes, as
  with `inspect`). It is never auto-spawned by a plain CLI call. It
  re-reads nothing from the environment after start.

**Discovery and trust: requirements for step 9.** The first version of
this section had the server check its clients but not the reverse. Before
step 9's code, and before anyone is told the daemon is safe to turn on:

- **The client checks the server before it sends anything.** The socket's
  directory must be a real directory the client owns, with mode 0700. The
  socket in it must be owned by the same uid. The connected peer's uid
  must be the client's own (`getpeereid` / `SO_PEERCRED`, from the
  client's side). Any failed check means the direct path.
- **Where the socket lives:**
  - macOS: under `confstr(_CS_DARWIN_USER_TEMP_DIR)`, not `$TMPDIR`;
  - Linux: under `$XDG_RUNTIME_DIR`; with none set (cron, containers,
    sessions without a login manager), **no daemon**;
  - Windows: the server creates the named pipe with
    `FILE_FLAG_FIRST_PIPE_INSTANCE` and an owner-only ACL, and the client
    checks the pipe's owner.
- **The handshake names the file.** A client sends the identity and the
  header seal it just read from page 0 (no key needed to read them). The
  daemon answers only if they match the file it has, under the lock;
  otherwise the client goes direct. The identity changes at every
  compaction, so the daemon re-publishes its socket when its file's
  identity changes.
- **"Same user" includes sandboxed processes.** Agent tools run commands
  in sandboxes and containers that are denied the brain file and the
  config holding its secret, but commonly allowed the temp directory and
  local sockets. A daemon gives those processes the brain. The docs say so
  in those words. Step 9 considers a per-daemon token that a client must
  present, kept where only an unsandboxed client can read it (next to the
  brain, 0600), so reaching the socket isn't enough.
- **Through the daemon, any client can act as any agent.** Claims, inboxes
  and presence are keyed by an agent id the client states. That's already
  true of anyone with the secret; the daemon removes the need for the
  secret. The docs say it with the point above.
- **Revocation.** A plain `rekey` doesn't stop a running daemon (the data
  key is unchanged, as the engine documents). After a compaction or a
  rotation with a new secret, a daemon that can't reopen the file exits;
  it doesn't retry. `mnemo daemon stop` is part of changing a passphrase,
  and the docs say so.

### The trust boundary (since RB-006)

- **Under (A), every process needs the secret.** A shared handle **keeps
  its secret for its whole life**, which today's handle doesn't (it keeps
  the data key and drops the secret once the file is open). It must,
  because every compaction gives the file a new data key, and without the
  secret every `mnemo compact` would end every session. A passphrase is
  worth more than a data key: it survives a rotation, and people reuse
  them. It now sits in a long-lived process's memory, often for hours, and
  the docs say so.
  - For a raw-key file the kept secret is the key itself, which changes
    nothing.
  - **At 12.3 (the keychain),** prefer fetching the secret again when it's
    needed over keeping it, and keep it only where there's nothing to ask.
- **Under (B),** while the daemon runs, any process running as the same
  user (sandboxed ones included) can read and write the brain through the
  socket without the secret. That's the ssh-agent model, and why the
  daemon is opt-in.

No new engine measurement was needed for this note. Step 5's bench adds

|---|---|---|
| Open, fast KDF (the reload cost) | 3.22 ms | 29.66 ms |
| Open, raw key | 2.90 ms | 30.10 ms |
| Open, secure KDF | 16.94 ms | 44.22 ms |

MEM-1's "232 ms to open an indexed 100K file" is the v8 number. v9 opens
the same corpus in about 30 ms, but its first recall loads the resident
fp16 column, about 112 ms at 100K. Below 20K facts (`V9_ANN_MIN_FACTS`)
there is no ANN index.

**So:** at 10K, a full reload plus first recall is about 12 ms, which (A)
can pay on every call where another process wrote. At 100K it's about
142 ms, which (A) can pay occasionally but not on every call, so the
incremental catch-up is the work that makes (A) good there. For hooks,
the bigger cost is the KDF on every fresh process (about 14 ms extra). 12.3's
keychain raw key removes it under (A), and the daemon removes it under (B).

**Hooks pay the KDF until 12.3 ships, and that's accepted.** 12.4 comes
before 12.3 (the keychain), so a passphrase file's hook opens with the
secure KDF in every process, about 14 ms more than a raw-key open at 10K.
Hooks also pass a short `--wait 2s`, so a busy file delays a session's
start by at most about two seconds. 12.2's spec records the 2 s figure.

## Claims and presence (since RB-006)

These are designed here and shipped as API in 13.3 (step 7). Both use the
lock and staleness machinery above.

**Since RB-006, step 7 reworks the probe and lapsing below.** REVIEWER-B
found the lock probe wrong in several ordinary cases:
- a holder whose forked worker survives it;
- a deleted sidecar directory;
- two probes at once;
- an agent with no long-lived process;
- a restart.

"A dead holder's claim lapses at once" turns each of those into a claim
taken from an agent that is still working. Step 7 brings:
- **claim tokens:** `renew`, `release` and a new `check(topic, token)`
  return `Lost` when the live claim's token differs, and an agent checks
  before an irreversible step;
- **the early lapse as a hint only:** only for a holder that registered a
  presence lock when it claimed, and has been not-alive for a short grace
  period (seen twice). Otherwise a claim lapses at `expires_at`;
- presence files re-checked by identity on every call;
- a probe that retries once before it says "alive";
- the clock's steps;
- claims and presence left out of 13.7's merge.

The text below is the shape those changes refine.

### Presence: liveness from locks, activity from commits

The spec says presence is a heartbeat record "at most once a minute,
piggybacked on a commit". It splits into two signals, because a heartbeat
that commits on its own would cost a durable write per agent per minute.
That's about 57 KB of file growth per single write in v9, plus a snapshot
per commit, which would push real restore points out of the 24-hour
retention window.

- **`alive` (free).** Each shared handle that declares an agent id holds a
  shared lock on its own sidecar file for its lifetime:
  `presence/<hash of agent id>.lock` in the sidecar directory, through
  `LockedFile`. To ask "is X alive?", try an exclusive lock on X's file
  without waiting.
  - Acquired: X's process is gone. The kernel released it, even after a
    `kill -9`.
  - Refused: X's process is running.

  No writes to the brain. (Not on iOS; see "Mobile".)
- **`last_active` (piggybacked).** The `_mnemo.kind = "presence"` record
  (agent id, role, tool, `last_active`) is updated only inside a commit the
  agent makes anyway, at most once a minute. It answers "alive but idle for
  three hours", which is what "out of usage" looks like (the session's
  server is still running, but nothing happens).
- **`who()`** returns both, for each known agent.

### Claims: compare-and-set inside the exclusive window

- **The record.** A claim is a `_mnemo.kind = "claim"` record: topic,
  holder (agent id), `expires_at` (wall clock), and a `lease` in seconds.
- **`claim(topic, ttl)`** runs in one exclusive window: catch up, read the
  live claim for the topic, and decide.
  - The topic is free if there is no claim, or the claim has lapsed (see
    step 7's rule above).
  - If it's free, write ours and commit, and return `Claimed` with its
    token.
  - Otherwise return `HeldBy { agent, expires_at }`.

  Two processes can't both win, because the second one's window starts
  after the first one's commit, and its catch-up sees that claim.
- **`renew` and `release`** run in the same kind of window.
- **The clock.** It's one machine, so one clock, and wall-clock times
  survive a reboot. A claim taken just before a laptop sleeps simply
  expires, and its holder learns that from `Lost`.

**Keyed records, not new types.** Claims and presence are ordinary keyed
records (12.1), with slot `claim:<topic>` or `presence:<agent>` and the
shared scope. Supersession gives each its history. `export --git` leaves
them out (R-006.2 (d)).

**Tests,** with the spec's three, plus:
- two processes race for one claim 1,000 times: exactly one wins each time;
- a holder is killed mid-claim: the other process gets the claim after the
  grace period through the lock probe, and at `expires_at` with the probe
  disabled;
- a holder that lost its claim gets `Lost`;
- every wait has a deadline;
- the FLAKE-1 pattern on the presence locks.

## 13.1b wake-ups under each option (since RB-006)

A wake-up needs something that sees every commit and can reach every
session.

- **Under (A),** each session's `serve --mcp --shared` watches the file:
  kqueue `EVFILT_VNODE`/`NOTE_WRITE` on macOS, inotify `IN_MODIFY` on
  Linux, `ReadDirectoryChangesW` on Windows, with a slow poll of the header
  stamp (every 30 s) as a safety net.
  - **The watch holds a descriptor** between calls (no lock). After a
    compaction it would be watching the replaced file, so it re-arms on
    rename and delete, or watches the directory and ignores the sidecar's
    `lock-info` writes.
  - **On a change,** it waits briefly (debounce), takes the shared lock,
    and checks the stamp. Only if the stamp moved does it catch up and
    query its own role's inbox for `sent` items.
  - **For each one,** it pushes a channel event, or a
    `notifications/resources/updated` (13.1b), and marks it `delivered`
    in one exclusive window.

  **The cost is a catch-up per foreign commit per session**, not just a
  header check: by the numbers table, 3.2 ms at 10K and about 30 ms at
  100K. Marking an item `delivered` is another commit, which wakes everyone
  again. Nothing happens while the file is quiet. The delivery state stays
  the source of truth, so a missed event loses nothing: the next turn's
  hook sees the item.
- **Under (B),** the daemon knows of commits made through it without
  watching, and it holds the connections, so it pushes to the right
  session's server directly. It still watches for direct writers.
- **`mnemo watch`**, which starts a session when work arrives for a role
  with none open, is a long-lived process under either option. It's the
  natural host for the daemon later.

The guardrails (rate limits, hop cap, kill switch) live in the code that
marks items `delivered`, so they're the same under both options.

## Readers: `inspect` and the CLI's read commands (since RB-006)

| | Today | Under (A) | Under (B) |
|---|---|---|---|
| `inspect` | Opens read-only, reads everything, closes (`inspect.rs`), so it never holds a lock while serving. Gets `Locked` while any writer is open | The same code. With writers holding locks only per call, the read-only open waits (bounded backoff instead of today's immediate `try_lock` failure), tens to hundreds of milliseconds while a writer is busy. A crashed writer's pending WAL gives `NeedsWriteOpen` ("any writer's next call recovers it"); `inspect` never writes | The same, direct. Optionally `/api/reload` asks the daemon for a dump, to skip the KDF on each reload |
| CLI reads (`info`, `list`, `recall --no-track`, `export`, `verify`) | `open_read_only` and `try_lock`: `Locked` while a writer is open | Wait with a deadline (`--wait`, default 10 s), then run alongside other readers | Use the socket when a daemon answers, else direct |
| CLI writes (`remember`, `update`, `compact`) | `Locked` while an MCP server is open | One exclusive window each; `compact` as below | Through the daemon if present (`compact` goes direct, see below) |
| A hook (`recall` at session start) | `Locked` while the session's MCP server is open | Works; pays the KDF per process unless 12.3's raw key is in the keychain | Works; no KDF |

## Worktrees (R-006.2 (a))

- **The path.** The default brain path resolves through
  `git rev-parse --git-common-dir`, so every worktree of a repository
  names the same file.
- **The lock (A)** is on that file itself, so worktrees need nothing more.
  Hard links and symlinks also agree, because `flock` is per inode.
- **The sidecars** (the `X.mnemo-shared/` directory) live next to the
  brain, at the one path every worktree resolves to, so a worktree's
  removal touches none of them. When the brain is inside a working tree
  (as `test/project.mnemo` is), the `.gitignore` pattern keeps them out
  of commits.
- **The daemon's socket (B)** lives in a per-user directory, not in the
  repository, and the handshake checks the file (see (B)). So all
  worktrees reach one daemon.
- **A `--personal` brain** (R-006.2 (e)) is a second file with its own lock,
  sidecars and (optional) daemon. A session can hold shared handles on
  both.

## Mobile (MOBILE-2) (since RB-006)

iOS and Android can't run a daemon, so (A) must stand alone there, and it
does.
- **iOS.** The reason for MOBILE-2's background rules is that iOS kills a
  suspended app holding a file lock in a shared container (`0xdead10cc`).
  - A shared-mode store holds no lock between calls, so suspension between
    calls is safe.
  - Today's "while inactive, reopen, work, flush and close inside an
    expiring background activity" becomes "lock, work, commit, unlock
    inside the activity". The reopen (and its few milliseconds) goes
    away; the activity wrapper stays.
  - **The wait is cancellable** (see "The protocol"): the store passes a
    deadline no longer than the activity's remaining time, and its expiry
    handler cancels a call still waiting. That call releases every lock
    before the app is suspended.
  - **No presence lock on iOS**, since it's held between calls. With
    mobile's opt-in, iOS reports `last_active` only, or holds the presence
    lock just for each call.
  - Also with mobile's opt-in:
    - the Swift and Kotlin stores create the sidecar directory themselves,
      through the same policy as the brain's directory (protection class,
      excluded from backup);
    - the docs say what a read-only extension does with `NeedsWriteOpen`.
- **The real multi-process case on phones** is an app and its extensions
  (a share extension, a widget, a notification service) on one App Group
  file. Today the second store gets `Locked`. In shared mode they take
  turns per call.
- **The default stays as it is** for a single-process app (open
  exclusively, on iOS only while in the foreground; coalesced commits).
  Shared mode is opt-in for App Group files, because it gives up
  coalescing (above).
- **Android.** The file stays open today because Android doesn't kill for
  a held lock. Shared mode is opt-in for the same multi-process cases.
  Linux's filesystem allow-list names ext4 and f2fs.

## Format (since RB-006)

**Neither option needs a format change.** The stamp uses what every v9
header already has:
- the header's seal (its nonce and tag), sealed since v7 under the data
  key;
- the file's identity, from the filesystem.

Incremental catch-up uses v9's existing generation-tagged delta chains.
Taking the generation lease per window uses the existing header-only
transaction. Claims and presence are `_mnemo.*` metadata on ordinary
records. The sidecar files and the socket are outside the brain.

Shared mode is v9-only: a v8 file opens read-only, as today. If
implementation finds it does need a header field, that goes through the
format-version policy (AGENTS.md) with its own design check. Nothing here
expects it to. Gating pre-0.14 binaries by format version is the one
format question left, and it's decided before step 8.

## Gaps in today's code, fixed in v0.14.0 step 1 (since RB-006)

Both gaps are fixed on `release-0.14.0` (PR 63), with tests that run on
every CI OS.

1. **`compact_file` dropped its lock before the rename.** It now holds the
   old file's exclusive lock through the rename and the directory sync.
   Every open checks, once it holds its lock, that the path still names
   the locked file, and retries if not.
   - Against v0.13.2's code the new race test lost 149 of 150 acknowledged
     writes (REVIEWER-B: 207 of 278). A writer retrying on `Locked` took the
     lock at the moment it was released, before the rename. With the fix,
     none are lost.
   - **Windows and the toolchain.** Renaming over a file another handle
     holds open works on Linux and macOS, and on Windows when the engine
     is built with Rust 1.85 or later (probed on CI: 1.75 to 1.84 refuse
     with os error 5, 1.85 to 1.100 succeed). The released binaries and
     wheels are built with stable.
     - Built with an older toolchain, compaction closes the old file and
       retries the rename, as before. The identity check before each
       commit then catches nearly every write that would land in the
       replaced file.
     - On those toolchains, Windows also refuses the rename while *any*
       handle has the file open. So compaction there fails (with an error,
       losing nothing) while other processes keep opening the file, as in
       v0.13.2.
     - **Shared mode on Windows refuses to start on a build made with Rust
       before 1.85** ("shared mode on Windows needs a build with Rust 1.85
       or later"; `build.rs` reads the compiler's version). The released
       binaries and wheels are built with stable, so users don't see it.
       The `windows-msrv` CI job (Rust 1.75) tests the refusal and the
       compaction fallback.
   - Compaction's and the exports' temp files are always new files under
     unique names, created only if nothing exists at the name.
   - Found on the way: `Mnemo::create` truncated the path before it tried
     the lock. It now truncates only once the lock is held.
2. **A handle couldn't tell the file was replaced.** Each commit and
   `rekey` now checks that the path still names the handle's file, and
   refuses with `MnemoError::Replaced`, writing nothing, if not. Shared
   mode's per-call check (protocol steps 4, 5 and 8) builds on it.
   - **Every compaction gives the file a new data key**, not only a
     rotation: `compact_file` builds the new file with `create_secret`,
     which draws a fresh salt and data key, and restarts the counters. So
     a shared handle that lives through any compaction needs its kept
     secret to reopen (one KDF run). That's why it keeps one (see "The
     trust boundary").
   - If the secret changed too (`rekey` then `compact`), the reopen fails
     with `WrongPassphrase`. That's the right result: rotation revokes
     running sessions that only know the old secret.
   - A plain `rekey` (no compaction) keeps the data key, so running
     handles keep working. That matches today's documented property that
     `rekey` alone doesn't revoke a data key someone already has.
3. **`try_lock` with no wait** in `open_with_lock` becomes the bounded
   backoff for shared and read-only opens, in step 2. Exclusive opens keep
   failing at once, as today, so existing callers keep their behaviour.
