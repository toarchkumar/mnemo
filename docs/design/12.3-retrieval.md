# 12.3 Retrieval: design note

Status: **accepted by PLANNER-A (2026-11-14), with TOK-1 as option 2 and a
staleness stamp; this is what step 4's code does.** Two choices made in the
code are marked **(code)**: the tokenizer is recorded as a mark inside each
keyword segment (section 3), and the question's own words get half the
weight of keywords given (section 2), from the measurements in section 5.

- Spec: PLAN.md, Phase 12, section 12.3, item 4 (R-007.2 recs 2 to 5),
  PLANNER-A's step 4 dispatch, and the TOK-1 decision (both 2026-11-14).
- Code references are to `release-0.15.0` after PR 83.
- No format change: the format version stays 9, and nothing new goes into a
  persisted MessagePack struct.

## 1. The query side

**The trait.** `Embedder` gains

```rust
fn embed_query(&self, texts: &[&str]) -> Result<Vec<Vec<f32>>> {
    self.embed(texts)
}
```

Every recall by text calls it. Everything stored calls `embed`.

| Query side (`embed_query`) | Document side (`embed`) |
|---|---|
| `RecallRequest::from_text`; the CLI's `recall --text`; the MCP `recall` tool with `text` (and its unlocked pre-embed); Python's `recall_text` | `remember_text`, keyed upserts and `update_text`, essence items, threads and `commit_deltas`, the CLI's ingest and `remember --text`, the MCP `remember` tool, and `reembed` |

The semantic result cache (`cache_put_semantic` and `cache_get_semantic`
with `text`) keeps `embed` on both sides. Both sides hold the same kind of
text (a prompt), and the entries already in a file stay comparable.

**The identity.** `EmbedderIdentity` gains `query_convention: String`. It's
empty when queries are embedded like documents, and otherwise a short name
for how `embed_query` differs, such as `bge-query-instruction`. The
identity check compares it with the other three fields, so a file embedded
one way refuses an embedder that queries another way, with the existing
`EmbedderMismatch` error. `reembed` is how a file changes convention.

- **Stored** as a `query_convention` key in the two JSON identities (the
  manifest's `metadata.embedder` and the `_mnemo.embedder` cache entry),
  **only when it isn't empty**. An existing file's identity reads as
  empty, so nothing changes for it, and a symmetric embedder writes the
  same bytes as v0.14.
- **Older builds** ignore the key. A v0.14 build would accept an
  asymmetric file's embedder by its other three fields and embed its
  queries with `embed`: worse recall, not corruption. The CHANGELOG says
  so.
- `EmbedderIdentity` derives `Default`, so a struct literal can end with
  `..Default::default()`. Adding a public field is a breaking change for
  Rust callers who build it by hand (CHANGELOG Changed).

**`--embed-cmd`: the side goes in each request.** A new flag,
`--embed-query <convention>`, says the command embeds queries differently.
With it, each request line is a JSON object,
`{"kind":"query","text":"…"}` or `{"kind":"document","text":"…"}`, and the
identity records the convention. Without it the protocol is unchanged (a
JSON string per line) and the convention is empty, so every existing
embedder command keeps working.

An environment variable (`MNEMO_EMBED_KIND`) can't do this: one child
serves a handle for its whole life, the MCP server's included, and embeds
both sides, so the side has to travel with each request. A variable would
mean two children and two model loads.

**Python.** `set_embedder(fn, *, name, dimensions, normalize=True,
query_fn=None, query_convention=None)`. `query_fn` has `fn`'s shape and
embeds queries. Pass both new arguments or neither; one without the other
is a `ValueError`. Today's one-argument callables work as before.

**Mobile (UniFFI) is unchanged.** Its identity has no convention, so an
asymmetric file is refused there with the mismatch error, which is the safe
answer. A query-side callback for Swift and Kotlin can come with the
built-in embedder (step 5).

## 2. Hybrid recall by default

**The rule.** A recall by text with no `keywords` also scores the text with
BM25. Explicit `keywords` replace the text for BM25, with today's weight
(ε = 0.5), so a caller who passes them gets today's results.

**The text's weight is 0.25 (code).** A question's common words ("how",
"the", "why") match unrelated memories, and BM25 is divided by the query's
best score, so the best common-word match gets the whole weight. At 0.5, on
this project's brain, a memory with similarity 0.18 came second on "how
releases are approved", 0.02 behind the right fact. At 0.25 the right fact
led all three questions by 0.26 to 0.42, and the only memory new to any top
3 (against vector-only recall) had similarity 0.37 (section 5). `RecallRequest::text_keyword_weight` sets it
(`DEFAULT_TEXT_KEYWORD_WEIGHT`); Python's `keyword_weight=` sets both.

- **The library.** `RecallRequest` gains `text: Option<String>`, which
  `from_text` sets. Recall uses it for BM25 when `keywords` is `None`. On a
  v8 file (read-only, no keyword index) the text is ignored, so a v8 recall
  by text works as before instead of failing as explicit keywords do.
- **The opt-out is empty keywords** on every surface: `.keywords("")` in
  Rust, `keywords=""` in Python, `"keywords": ""` in the MCP tool, and
  `--no-keywords` (or `--keywords ""`) in the CLI. Empty keywords mean
  vector-only recall.
- **The guidance changes.** The `keywords` docs said not to paste the
  question. They now say the question is used already, and keywords are
  for identifiers the question doesn't contain.
- CHANGELOG Changed: results change for callers who recall by text without
  keywords.

Section 5 has the measurements.

## 3. TOK-1, tokenizer v2

**The tokens.** Tokenizer 2 keeps every tokenizer 1 token (UAX #29 words,
lowercased, plus the compounds) and adds the parts of each token:

- split on `.`, `/`, `_`, `-` and `::`, keeping non-empty parts;
- a possessive (`'s` or `’s` at the end) also gives its stem;
- **no part that is only digits (code):** the `9` and `0` of `v0.9.0` would
  match nearly every versioned text. `v0` is kept, and the whole `v0.9.0`
  still matches the version exactly.

So `mnemo.nosync` gives `mnemo.nosync`, `mnemo` and `nosync`, and
`iCloud's` gives `icloud's` and `icloud`.

**Each distinct term counts once per whitespace run (R-008.2).** Tokenizer
1 emits a dotted name twice (UAX #29 keeps `mnemo.nosync` whole, and the
compound pass adds it again), and UAX #29 already gives `key` and `file`
for `key-file`. Tokenizer 1 stays as released, since v0.12 to v0.14 indexes
depend on it. Tokenizer 2 takes, per run, its UAX #29 words, its compound
and their parts, and counts each distinct term once; a term in two runs
counts twice. `mnemo.nosync key-file open_shared Mnemo::open iCloud's`
gives every term `tf` 1 except `mnemo` and `open` (2), and the document's
length is the sum. Queries take the same terms, deduplicated. The 64-byte limit still applies. (UAX #29 already
splits `std::fs` into `std` and `fs`; the compound `std::fs` is the whole.)

**One tokenizer per index, as far as v0.15 goes.** v0.15 splits every
document it writes and every query with the file's tokenizer, so it never
mixes the two itself; only an older build's write can (below). A file keeps
tokenizer 1 until its BM25 index is rebuilt. **Compaction and
`reembed` rebuild it**, since both write a new file whose index starts
empty. New files start at 2.

**Why not the manifest byte.** The BM25 manifest has a `tokenizer` byte for
this, but every v9 build released so far (v0.12 to v0.14) checks it when it
opens a file (`load_bm25_manifest`, called from `open.rs`) and refuses
anything but 1. A file v0.15 created or compacted wouldn't open in v0.14 at
all, a phone app on v0.14 included. **The decision (PLANNER-A, option 2):**
the byte stays 1, and the tokenizer is recorded where older builds carry it
untouched.

**Where it lives: a mark in each segment (code).** A keyword segment v0.15
writes with tokenizer 2 carries a reserved term, `"\0mnemo.tokenizer.2"`,
first in its dict, posting document 0. A segment merged from tokenizer 2 and
tokenizer 1 documents carries `"\0mnemo.tokenizer.mixed"` instead. Nothing
tokenizes to a term that starts with a NUL, and document 0 is never live, so
no query matches the mark and every merge drops its posting.

- **Why not the manifest memory's metadata,** the place PLANNER-A preferred:
  only `mnemo init` writes a manifest. A file from `Mnemo::create`, Python's
  `open` or the mobile binding has none, so the record would need a second
  home. And the stamp the decision asks for would have to be rewritten on
  every commit that indexes a document: one more record a commit.
- **Why not a reserved cache entry:** the same per-commit rewrite, and it
  would need exempting from eviction, TTL and `cache clear`.
- **The mark is its own staleness stamp.** It's written with the segment it
  describes, in the same commit, at no extra write. An older build leaves
  existing segments as they are, and what it adds has no mark:
  - its write adds an unmarked segment;
  - its merge rebuilds segments without the mark, because the mark's only
    posting is document 0, which the merge drops;
  - its compaction rebuilds the whole index unmarked.
- **If a mark is lost anyway,** the segment counts as tokenizer 1, which
  degrades safely: whole tokens still match.
- **The mark is score-neutral (check 3).** BM25's N, average length and
  each document's length come from the rows, not the segments; the mark's
  only posting is document 0, which no row has; and no query tokenizes to
  it. Tested: the same documents with their segments marked and with the
  mark left out (a dev hook) give identical raw BM25 scores for a query of
  whole words.

**The file's state** comes from its segments' marks and the handle's pending
documents (`KeywordTokenizer`, in `Stats` and `VerifyReport`):

| Segments | State | New documents and queries use |
|---|---|---|
| none yet | 2 | tokenizer 2 |
| every one marked 2 | 2 | tokenizer 2 |
| none marked | 1 | tokenizer 1, so the index stays pure until it's rebuilt |
| some of each, or one marked mixed | mixed | tokenizer 2 |

**How a mixed index is queried:** with tokenizer 2. A query's whole tokens
match every document, since tokenizer 2 indexes every tokenizer 1 token. Its
parts match only the tokenizer 2 documents. A v0.15 merge of a mixed index
is marked mixed, never 2, so it stays mixed until a compaction or `reembed`
rebuilds it at tokenizer 2.

**Reported:** `mnemo info` shows `keywords: tokenizer 1|2|mixed`, with a note
that `mnemo compact` rebuilds it; `mnemo verify` notes a mixed index; Python's
`stats()["keyword_tokenizer"]`; the inspector's `keyword_tokenizer`.

**Tested:**
- `tests/tok1_compat.rs`, against the published v0.14.0 CLI, in CI's new
  `compat (v0.14.0, linux)` job (the `old compactor` job's pattern):
  - a tokenizer 2 file opens, recalls by keyword, verifies and takes an
    import under v0.14.0;
  - v0.14.0's import makes it mixed, v0.15 reports it, and a compaction
    heals it;
  - v0.14.0's compaction leaves tokenizer 1, which v0.15 keeps pure, and
    which a v0.15 compaction moves to 2.
- `tests/retrieval.rs`, on every run: a committed v0.14.0 fixture
  (`tests/fixtures/tok1/`) opened, queried, written, then rebuilt; and a
  mixed index made by a dev hook that writes as an older build does.

## 4. `mnemo reembed`

`mnemo reembed <file> --embed-cmd <cmd> --embed-name <name>
[--embed-query <convention>] [--embed-dims <n>] [--embed-timeout <s>]`
(and the global `--wait`), and `Mnemo::reembed_file` (`_with_key` and
`_waiting` variants, like `compact_file`). Step 5's built-in embedder adds
its own flag. Until then the CLI's embedder flags are the existing ones;
the spec's `--embedder …` was a placeholder.

- **It's a compaction with new vectors.** It runs under the file's
  exclusive lock, which it waits for as compaction does (`--wait`, 10 s by
  default). It writes a temp file beside the brain with the same salt and
  KDF parameters, then renames it over the brain while the lock is held.
  An interrupted run leaves the old file whole and a dead temp, which the
  next compaction or reembed removes. A file never opens with two
  identities or with mixed vectors.
- **Every live memory is embedded again** with `embed` (the document side),
  in batches of 64: facts, superseded versions (so history reads stay
  consistent), essence items and thread turns. A manifest and a thread
  link keep their sentinel vector at the new width and aren't embedded
  (R-008.3): a link's text isn't meaning, and its continuation lookup goes
  by metadata. `ReembedReport` counts the three groups.
- **The new identity is recorded** in the manifest's `metadata.embedder`
  and the `_mnemo.embedder` entry. Any other cache entry is copied as
  compaction copies it. A semantic entry keeps its vector and its `model`,
  so it matches only lookups under the old model's name.
- **The width can change.** The new file takes the new embedder's
  dimensions (`--embed-dims`, else the file's), so `reembed` is also how a
  file moves to a model of another width.
- **The embedding runs under the lock,** like a compaction's copy. For a
  big file, that's minutes in which other processes wait.
- **The BM25 index is rebuilt** with the current tokenizer.
- Like compaction, it drops snapshot history, and it reports what it
  copied.

## 5. Measurements

DOGFOOD-0's three questions on copies of `test/project.mnemo` (132
memories) in a scratch folder, read-only, with the project's embedder
(`sentence-transformers/all-MiniLM-L6-v2`, symmetric, through
`test/scripts/project_memory.py`'s Python callable, which reads `test/.env`;
the project has no `--embed-cmd` script). Tokenizer 1 is the brain as it is;
tokenizer 2 is a compacted copy. "Rank" is where the right fact lands;
scores are score / similarity. 2026-11-14, M1 Pro, this branch's release
wheel.

| Question | Before: vector only, tokenizer 1 | After: hybrid (0.25), tokenizer 2 | Best other, after |
|---|---|---|---|
| "how releases are approved" | **1**, 0.928 / 0.684 | **1**, 0.928 / 0.684 | 0.619 / 0.369 |
| "where the repo lives and why" | 2, 0.446 / 0.329 (first: the stale-folder fact, 0.470) | **1**, 0.785 / 0.329 | 0.523 / 0.354 |
| "what stops for the user" | **1**, 0.654 / 0.482 | **1**, 0.993 / 0.482 | 0.577 / 0.382 |
| "where the repo lives and why", `keywords="nosync"` (DOGFOOD-1's case) | 2: `nosync` matched nothing | **1**, 1.124 / 0.329 | 0.502 / -0.009 |

Measured after R-008.2's fix (tokenizer 2 counting a term once per run).
The first run, before it, on 129 memories, had the same ranks, with scores
within 0.054 (the last row's best other was 0.556).

- **Hybrid** puts the right fact first on all three. The repo question moves
  from second to first.
- **Tokenizer 2** changes nothing for the three questions (their words are
  whole words either way). It's what makes DOGFOOD-1's `nosync` find
  `mnemo.nosync`: under tokenizer 1 that keyword matched no token.
- **The text's weight.** The same questions at 0.5: the right fact still
  first, but on "how releases are approved" a memory with similarity 0.183
  came second at 0.907 against 0.929, through "how". On the repo question,
  the project mission (similarity 0.171) came second. At 0.25 the top 3s
  are vector recall's, reordered, except on the release question, where a
  status fact (similarity 0.369) comes second and the release-flow fact
  (0.468) drops out. At 0.1 the margins narrowed again (0.582 against 0.492 on
  the repo question). Hence 0.25.
- **The baseline for step 5's model comparison** is the "after" column.
